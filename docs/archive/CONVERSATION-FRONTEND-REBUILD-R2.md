## 1. 目标与范围

用户看见的是独立阅读视窗，不是随同步状态重新定位的页面。
视窗边界不由网络/任务状态驱动；用户输入内容和实际窗口尺寸变化可以调整可用高度，阅读位置按同一组件合同保持。
历史、新消息和缓存更新消息列表；只有用户操作、显式导航，以及已经处于底部跟随时的尾部增长，能改变阅读目标。
列表内部可为 prepend/resize 调整坐标，但同一可见内容的屏幕位置必须保留。
这个约束描述的是最终可见帧，不要求组件内部只执行一次计算。

视觉工作包替换会话展示模型、阅读状态、列表更新协议及虚拟列表接入，不全盘重写数据层。
但完整会话交互方案还必须关闭同步新鲜度、关键 attach、控制投影权威及提交持久化合同，
不能把它们一律称作外部输入后又宣称覆盖所有用户场景。相关后端/数据修改另列工作包，
本轮审核不实施这些修改，也不把已有正确的 Replica/Meta 快路推倒重写。
不改输入框外观、等待区外观/默认展开、移动频道目录和导航拓扑。
不建立新的 DOM 行高数据库、不接管原生惯性滚动、不把整个频道挂进 DOM。

### 1.1 建模起点：用户意图，不是故障列表

会话页面的职责是让用户进入一个会话、阅读内容、定位内容、操作内容、输入消息，再离开并恢复。
故障是这些交互合同被破坏后的表现。设计必须先定义正常行为，再推导边缘情况。

模型采用有限的事件族，而不是穷举无限多的消息正文、坐标和事件序列。
一个事件由 `source + intent + target + identity/version` 描述；像素、消息 ID、正文只是参数。
同一业务操作无论从鼠标、触摸、键盘还是辅助技术发起，进入同一个语义入口。

事件来源严格分成三类：

- 用户/路由：进入、离开、阅读、导航、内容操作、输入和发送，有有限且明确的控制权限。
- 环境：视口/键盘/字体/媒体/组件生命周期变化，没有创造阅读目标的权限。
- 后台事实：历史、live、Meta、缓存、receipt、控制状态，只更新其权威模型。

一个 DOM `scroll` 或 `resize` 不是用户意图：它也可能由浏览器、列表补偿或程序定位产生。
不能直接用它把 browsing 改回 following；必须有仍有效、属于消息滚动容器的用户操作证据。

### 1.2 状态空间：正交组合，不是巨大混合 mode

| 维度 | 状态/数据 | 唯一 owner | 生存期 |
|---|---|---|---|
| 会话身份 | principal + channel + viewKey；activationID | ConversationSession | 一个视图的激活期；每次进入产生新的 activationID |
| 页面生命周期 | inactive / opening / active / suspended | ConversationSession | 激活期；不代表连接是否成功 |
| 阅读意图 | following / browsing | ReadingSession | 按会话/视图保存；加载、断线不改变它 |
| 阅读书签 | messageID、可用时 blockID/文字位置、视窗内 offset、邻项线索 | ReadingSession | 跨虚拟回收和频道切换；与尺寸缓存分离 |
| 用户接管版本 | inputEpoch、readingRevision、当前手势归属 | ReadingSession/输入边界 | 当前激活期；迟到导航必须校验 |
| 显式导航 | idle / resolving / executing / failed；commandID/target/reason | ReadingSession | 一个命令，成功/失败/取消均终止；不无限重试 |
| 数据可用性 | empty-known / partial / sufficient；范围 coverage | Replica | 数据身份内；没有消息与还不知道是两回事 |
| 历史需求 | idle / loading / exhausted / error；语义范围、requestID | HistoryDemand | 可取消/替换的需求；不持有阅读目标 |
| 同步新鲜度 | transport、attach、hydrate、catch-up 独立状态 | SyncSession | 连接/同步期；generation 不等于视图身份 |
| 展示数据 | immutable revision、稳定消息身份、变更集合 | Presentation | 当前会话数据投影；不得隐藏可变 getter |
| 展示选择 | 展开、线程/详情、图表模式 | PresentationChoices | 稳定内容身份；DOM 卸载不能删除选择 |
| 输入状态 | 草稿、回复目标、附件、输入法 composition | Composer | 按频道隔离；发送失败保留可恢复意图 |
| 当前任务 | current / stale / unknown 的权威投影 | ControlProjection | 后端版本/完整性边界内；不是展示选择 |
| 物理布局 | 尺寸、窗口、坐标、测量缓存 | MessageList | 组件私有、可丢弃；不得覆写上述业务状态 |

例如 `active + browsing + history.loading + transport.disconnected` 是合法组合。
不能为它新增一个“恢复中”总状态并借此获得定位权。
首次 opening 尚无内容时可以没有书签；已有内容不得因重新 loading 被替换成整屏空白。

### 1.3 用户行为全集（当前会话产品范围）

下面是语义事件分类。每个入口必须有 owner；尚未提供的产品功能无需新增 UI，
但未来接入搜索/深链等入口时必须遵循已有导航合同，不能另建控制器。
`保位` 指保留提交当刻仍存活的阅读内容相对于视窗的位置，包含用户等待期间产生的运动。

| 事件族 | 包含的行为 | 状态/副作用 | 阅读与定位规则 |
|---|---|---|---|
| U01 进入 | 首次打开、选择其他频道、路由/深链进入 | 激活隔离的 session；立即校准当前频道 Meta；加载目标所需数据 | 优先级为本次明确导航目标 > 已保存阅读意图 > 新会话尾部；initial target 每次激活只决策一次，分批到达不是重复初始化 |
| U02 再选择当前频道 | 点击已选频道、明确刷新内容 | 校准新鲜度；保留同一视图身份 | 不因为 reselect/refresh 重置定位；若按钮语义是“回最新”则走 U08 |
| U03 离开/返回 | 切频道、浏览器前进后退、打开后返回 Preview/线程页 | 保存同一已提交 readingRevision；旧激活期异步回调失效 | 恢复语义目标一次；following 不恢复旧物理中间位置 |
| U04 向上/离尾阅读 | wheel、touch、滚动条拖动、PageUp/Home、辅助技术滚动 | 用户接管，取消过期导航；进入 browsing | 运动由浏览器/列表执行，后台不得拦截、反向修正用户意图 |
| U05 向下阅读 | wheel/touch/键盘/拖动，含反向和惯性延续 | 更新书签；方向不是持久“允许钉底”的布尔值 | browsing 中向下未到尾仍是 browsing；一次有效用户操作确实到尾才 following |
| U06 到达数据边缘 | 顶部、最老历史、短列表同时接近两端 | 更新需求；exhausted 后无重复请求；错误允许显式重试 | 接近顶部不是导航，短列表 atBottom 也不是跟随授权 |
| U07 暂停/选择/复制 | 停止滚动、选择正文、复制、拖选自动滚动 | 保留选择/焦点；正文选择期间暂停自动跟随授权 | 不因几何变化恢复 following；复制结束不自动跳尾，允许 U05/U08 恢复 |
| U08 回到最新 | 点击最新/未读提示中明确的“回最新”、产品级 End 命令 | 授权一次尾部导航，设 following，校准新鲜度 | 不能把输入框内 End 当作消息区命令；用户随后接管使旧命令失效 |
| U09 指定消息导航 | 点击引用、搜索结果、未读起点、深链、跳转时间 | resolving 目标范围，再执行一个导航；设 browsing | 目标未到达时保留当前画面；目标不存在显示失败，不默认跳尾 |
| U10 改变视图 | scope/filter、线程视图切换、清除筛选 | 明确 viewKey/rebase；保存与恢复各自会话 | 保留仍可见锚点；否则选最近可见邻项；无匹配展示空结果而非最新 |
| U11 改变内容展示 | 展开/收起、过程详情、嵌套线程、图表模式 | Choices 提交一次变更；可见区域内操作取得 browsing 权限 | 保持操作目标及邻近阅读位置；不可保留被用户主动隐藏的文字；不全列表重置 |
| U12 消息业务操作 | 回复、编辑、重试、撤回/删除、reaction、任务控制 | 命令交给各自业务 owner；正文变化进入统一更新协议 | 操作本身不自动导航；删除锚点按邻项规则处理，不让按钮自行 scrollIntoView |
| U13 输入 | 聚焦、换行、粘贴、输入法、添加/删除附件、取消回复 | 只改变 Composer 状态；自然增高；等待区随输入栈顶部移动 | 不修改阅读模式或消息身份；焦点/软键盘变化走环境规则 |
| U14 发送 | 提交、失败、重试、取消待发送 | 本地意图/receipt/feed 按稳定身份合流；不冒充后端任务 | following 下正常随新增尾部；browsing 下默认保位，发送不是隐式跳尾命令 |
| U15 嵌套内容交互 | 代码横向/纵向滚动、详情内滚动、链接/文件/图表、弹层 | 事件属于实际操作容器；边界移交遵循原生行为 | 子容器滚动不改变主列表 following；关闭弹层恢复焦点不得让浏览器擅自滚动祖先 |
| U16 显式恢复/重试 | 重试历史、恢复连接、重新加载失败媒体/正文 | 只重试对应失败操作，保留可用内容与参数 | “重试成功”无定位权限；除非用户点的本来就是一个导航命令 |

### 1.4 后台与环境事件全集

| 事件族 | 事件 | 允许改变 | 不允许改变/必须保持 |
|---|---|---|---|
| B01 历史 | 请求开始、批次结束、重复页、失败、取消、exhausted | Replica/coverage、需求状态、稳定前缀 | 不保存/重放请求时屏幕位置；重复页不重复 prepend |
| B02 新消息 | live、catch-up、离线遗漏补齐 | 事实、展示、未读；可能出现中间插入，不仅 append | 不能以“最新数据到达”授权新导航；提交时为 following 才尾随 |
| B03 内容变更 | token、终态、编辑、撤回、删除、reaction、权限隐藏 | 对应稳定身份的 revision 或删除事实 | 不因 latest 变化更改折叠；不默认整篇重挂；失效锚点使用确定性替代 |

### 1.5 并发合同：不是为每对回调加补丁

三种版本不能混用：

- dataEpoch：服务端数据世界/账号的身份有效性；transport generation 仅用于拒绝旧连接答复。
- activationID/viewKey：这次页面激活与语义视图；离开的页面不能控制新页面。
- presentationRevision/readingRevision/inputEpoch：内容版本、阅读决策版本和用户接管版本。

以下是统一裁决规则，应用于任意长的事件序列：

1. 先检查身份和所属激活期，再处理事件；重复数据/命令幂等。迟到事实可归入正确频道的数据层，但没有当前页面控制权。
2. 每个 owner 串行提交自己的状态；展示提交基于已提交版本合成下一不可变版本，不允许多个来源分别 setRows。
   Replica 先接收事实；旧 baseRevision 的候选投影失效后，从当前事实/当前投影重算受影响项。
   丢掉陈旧候选数组不能等于丢掉那批历史或 live；也不能拿候选全量数组覆盖后来事实。
3. 数据准备不能携带稍后必执行的 `follow=true`。实际提交必须与当前 ReadingSession 一致：
   若 readingRevision/inputEpoch 已变，重新推导策略；不能丢掉新数据，也不能执行旧跟随授权。
4. 输入一旦实际归属于主列表或明确导航，旧导航令牌失效；触摸惯性仍属于同一用户阅读过程。
   新一条显式导航替代旧导航；组件已接收命令的取消属于组件门槛，不靠外部反向滚动补救。
5. 位置策略只有 preserve / follow / explicit-navigation 三种。一次提交只能选择一种；
   普通数据更新不产生 explicit-navigation，保位所需物理补偿不是新的业务导航。
6. 锚点变化归因：内容存在则保该内容；删除/过滤导致不存在则取旧顺序中最近存活后继，其次前驱；
   均不存在进入已知空视图。目标暂未加载不同于已删除，保留当前画面并解析目标，不跳尾。
7. 同一批发生 prepend、append、正文更新或中间插入，先形成真实变更集合，再选择一次位置策略。
   禁止把混合变化谎报成纯 prepend，禁止静默用 rebase/remount 兜底。
8. 书签/Choices 的晚到读取及卸载写入不得覆盖更新 revision；错误/取消不会撤销较新的用户操作。
   A→B→A 的两个 A 使用不同 activationID；session 内 revision 不随 remount 归零。
   持久写入检查所属激活期/版本；跨 tab 写入还需原子比较或明确冲突协议，本方案不声称已提供跨 tab 同步。
9. 到尾证据必须关联当前主列表用户操作及相容的布局版本；数据缩短、viewport 增高或程序性定位造成的
   atBottom 不得消费一个过期的向下手势。无法归因时保持 browsing，不保留无限有效的 tailArrivalArmed。

必须推导的组合至少包括：
`history×继续滚动/反向`、`live×离开尾部`、`resize×浏览/跟随`、`目标加载×切频道`、
`hydrate×live/用户选择`、`prepend×append×正文更新`、`导航执行×用户接管`、
`键盘×输入×新消息`、`删除/过滤×当前锚点`、`回收×展开/选择/焦点`。
这些是状态机交叉覆盖，不是仅从已报告 bug 复制的测试。

### 1.6 状态保持、可达性与性能预算

- 频道切换/回收：保存语义 mode/bookmark/Choices/草稿，尺寸缓存可丢弃；恢复 following 不得使用旧 scrollTop。
- 硬刷新：计划持久化小型、带 schemaVersion/principal/viewKey/revision 的会话记录；
  恢复迟到不得覆盖本次用户输入。草稿持久化由输入数据工作包承担，不假称当前已实现。
- 连接重建：保留阅读会话；只有权威数据世界不兼容才失效缓存，不能仅因 socket generation 变化全清阅读状态。
- 消息内控件：保留焦点/文本选择是 DOM 回收策略的约束，不能靠 key 稳定就宣称满足；
  不可无限 pin 行。有限保留或可恢复语义焦点的能力需组件验证；复制/输入不可被后台更新无提示打断。
- 读状态：收到消息不等于读过消息。前台激活且可见的已确认消息范围才推进 read frontier；
  在后台、被弹层遮挡、仅加载到缓存时不得标已读。协议能表达的粒度由数据合同约束。
  过滤视图只证明其展示集合被读到，不能用最大可见 seq 跨越未显示内容。
  若后端只有频道累积 cursor，未明确其“主动确认到此”或“连续已读”语义前，过滤视图不得自动推进它；
  显式标记已读属于独立用户授权。
- 浮层可达性：用户已确认自然输入/回复/附件增高可调整消息区可用高度；实际输入栈上方保留32px。
  网络/任务状态不改变尺寸；等待区默认展开和外观保留，有限视口下使用第15.7节尺寸预算与内部溢出。
- 性能：滚动输入路径不做全量投影/全文解析/大批同步挂载；内容变化仅失效依赖项。
  缓存/DOM/后台工作均有上界；记录数据就绪、展示就绪、DOM 覆盖三个阶段，区分网络等待与渲染跟不上。
  具体设备负载预算在集中验证前确定，不能用“无限速度下绝不空白”作不可检验承诺。

### 1.7 完备性判据

本模型覆盖的是当前产品能力，不声称穷尽未来所有功能。新增入口必须归入已有事件族，
或明确扩展模型及其权限，不能留下未归属的 effect/DOM 监听器。

设计审查按以下顺序，而不是从 bug 一条条修：

1. 逐一映射路由、按钮、手势、键盘、焦点、可访问性入口到 U01–U16。
2. 逐一映射网络、存储、计时器、组件和浏览器回调到 B01–B06/E01–E06。
3. 每个事件在 following/browsing、空/部分/充分数据、active/suspended、导航有无、连接好坏下都有处理或明确 no-op。
4. 每次状态写入只有一个 owner；每次位置变化能归因到用户、授权尾随或保位补偿。
5. 每个改变内容拓扑/几何的因素都映射到统一更新协议，不能以“特殊情况”绕开。
6. 最后将历史故障加入回归验证；没有用户报过的合法组合也必须从模型生成覆盖。

R2由第15节给出模型与机制，复审逐项结果见第16节；组件扩展已规定系统落点和维护边界，
浮层采用用户确认的内容驱动高度方案，不把责任藏在“适配层负责”五个字里。实施仍必须验证这些机制。

### 1.8 场景模型：从用户目的到系统完成义务

事件表用于定义有限输入，故障总账用于追溯证据；两者都不能代替场景模型。
场景描述用户要完成的事、起始条件、连续动作、系统应主动推进的工作、可观察结果及恢复路径。
用户说“看不到”“没拉新消息”“被拉回去”，是在指出某个使用过程未完成，不是在替工程师指定某个函数的bug。

#### J1 进入频道：我要看这个频道的内容和最新进展

入口包括首次打开、目录选择、深链、浏览器返回、同频道重新选择；不同入口的阅读目标可不同，
但不能有入口遗漏数据校准义务。进入不等于只有一次 `setActiveChannel`。

系统并行承担四项工作：

1. 建立本次有效会话身份及阅读目标；不等待正文或网络完成才接受用户操作。
2. 展示身份有效的已有内容；本地尚无内容则显示局部加载状态，不把未知显示成“没有消息”。
3. 主动向后端校准当前频道Meta；不能因已有缓存、socket已开、频道上次已访问而跳过。
4. 对照已证明coverage补齐到远端目标；内容到达沿原视图提交，不靠重挂或再次导航才出现。

| 起始条件 | 用户应看到什么 | 系统主动做什么 | 不算完成的情况 |
|---|---|---|---|
| 无本地内容，在线 | 可操作的频道壳与明确加载状态，随后出现可读内容 | 取得权限/会话、Meta和初始内容；几条路径不互相无谓阻断 | socket成功但页面永远空、只有下一次push才开始显示 |
| 有旧缓存，在线 | 先读已有内容；校准期间不冒充已追平 | Meta校准与缺口追赶；若用户开始浏览，继续供给但不抢位置 | 只恢复缓存就停止；local最大seq较大便误判完整 |
| 有缓存，离线 | 缓存内容可读、状态明确；输入遵循本地接受合同 | 保留同步义务，连接可用后继续 | 清空内容、永久取消追赶、假装当前任务已知 |
| 无缓存，离线/无权限/请求失败 | 分别呈现离线、无权、失败或可重试；不是统一空频道 | 正确归属错误及重试入口 | 无限转圈；用户不知道是真的空还是无法读取 |
| 后端明确为空 | 已知空会话，仍可按权限输入/订阅 | 保留live与后续校准 | 将空作为取消订阅或永久exhausted所有未来内容的理由 |
| 恢复历史书签/深链旧消息 | 定位对应阅读目标；新消息在其后可用 | 同时解析目标范围和校准最新状态，两者各有需求 | 为了拿最新内容把用户送到尾部，或为了保书签不再追新 |

完成判据分开：`可读`是已有可用内容，`已校准到H`是当前数据世界中已证明补齐到一次后端head H，
`已定位`是本次有效阅读目标已展示。三者不能用一个 loaded/connected 布尔值替代。
“校准到H”不承诺永远没有更新，而是可验证的本次新鲜度边界。

#### J2 留在频道/重新进入：我要持续看到进展，不靠碰巧再来一条push

进入、重选、回前台、回最新、手动重试建立或更新当前频道的同步兴趣。
live是正常增量路径，但不能是唯一的缺口发现路径；断连、丢帧、缓存恢复、后端已有内容但没有下一次push都必须能收敛。

同步义务由SyncSession/Scheduler维护，而不是MessageList effect各自发请求：

```text
兴趣动作 → 需要校准Meta → 得到本次有效head H
        → coverage未覆盖H所需范围 → 持续追赶
        → coverage证明满足 → 本次义务完成
```

- 同频道重复动作可以共享在途请求，但不能丢掉更晚的校准意图。
  请求携带 interestRevision；在途期间有新的校准动作则标记dirty，旧请求结束后再校准，
  不能把动作之前已经取得的head无限复用为“每次进入都检查过”。合并避免并发风暴，不取消最终一次校准。
- Meta与追赶请求均有终态和超时。超时/失败保留未满足义务，进入可见错误及有界退避/显式重试；
  不因一条失败静默停止，不在每次render或scroll事件重复开请求。
- 当前前台频道除兴趣动作外，还需连接健康/新鲜度校验机制作为漏push兜底。
  使用有界、可合并的轻量head校准；具体周期/退避预算归SyncSession配置，不用“只等下一条消息”代替。
  后台暂停和恢复有明确规则；恢复重新校准，不能执行积压的一串定时任务。
- Meta不等待正文批量解析、历史持久化或深历史预热；新鲜度追赶优先于后台预热。
  有限带宽下仍需为用户当前历史需求留出进展机会，避免一边追新一边饿死正在看的历史。
- 切频道后旧答复可更新其合法数据副本，但不得改变新频道优先级/导航。
- browsing/following只决定显示位置，不决定要不要同步。浏览旧内容时照样追新。

这一场景补足“有动作就应检查”背后的义务：动作建立的是最终必须满足的同步需求，
不是仅调用一次API然后无论成败都算做过。

#### J3 向上阅读：我要连续看更早内容，不是请求一次后被系统重新安排位置

起点可以是尾部、历史中段、冷缓存或重连后。用户可能慢读、快甩、停下、反向，
也可能连续触顶；这些动作始终属于同一次阅读过程。

- 在接近已知边缘之前传递范围需求，由Scheduler准备；历史返回时保持提交当刻的阅读内容。
- 用户等待期间继续移动，新的位置自然取代旧位置；请求不携带恢复旧画面的权力。
- 数据已在副本而DOM未准备好，与数据还没取得是两个问题：前者归展示/列表预算，后者归供给。
- 边缘未知、加载中、失败、已耗尽分别处理。不能为了消除抖动把旧消息入口封住，
  也不能为了“能滚”先释放整屏空占位。
- 成功判据同时包括旧内容可达、手势连续、锚点稳定、没有空窗和重复请求；只“不跳”不算完成。

#### J4 阅读中内容变化：我要继续读我正在读的地方

后台变化包括新消息、流式增长、终态、缓存合流和媒体完成；主动变化包括展开/收起、切详情、跳引用。
按变化来源决定权限，而不是按“这次高度差多少”决定是否跳转。

- 未改写的当前阅读内容保位；下方新消息增加未读，不改阅读目标。
- 用户主动展开/收起保住操作附近的阅读连续性；收起后的几何和可滚范围必须同步正确。
- 列表回收、消息不再latest、加载到父请求不能重新解释用户选择或搬动既有内容。
- 若文字本身被删除或宽度变化使重排不可避免，使用明确的语义替代；不伪装成普通prepend，
  不以整篇冻结、静默丢更新或跳最新规避。
- 用户在复制、编辑、操作控件时，焦点/选择属于交互连续性的组成，不只保障行顶坐标。

#### J5 输入、回复、发送：我要顺畅表达，不承担消息同步的代价

从点击回复、多行输入、输入法、附件选择，到发送、失败重试、切换频道保留草稿，是一个输入过程。

- 输入状态由Composer拥有，消息流式更新/历史解码不能迫使编辑器重挂或每键重算消息列表。
- 回复和正文自然增高；等待区贴着输入框上沿；连接文案只换固定状态栏内容。
- 本地接受、网络receipt、账本落地分别表示。发送失败不能静默丢稿、重复气泡或假称后端已queued。
- 用户在历史中发送仍保位；是否主动回最新是另一个动作。
- 消息阅读区/按钮可达性和输入栈布局必须一起满足，不能让“输入悬浮”变成“下面内容永远被盖住”。

#### J6 目录、会话、预览之间移动：我要换地方办事，再回来接着读

用户从移动目录进入频道、打开文件、下载或关闭返回，系统应保持每个Surface自己的几何和会话。

- 目录不受隐藏会话、任务状态、输入高度影响；Header不重新变厚。
- 手机Preview自己适配屏幕，超宽内容在自己的容器处理；不支持预览也有可用下载入口。
- 返回恢复对应阅读意图；旧页面卸载写入、恢复异步回调不得覆盖新会话。
- 这不是“消息区之外所以不测”的旁支：会话页面的真实使用过程包含进入和离开这些Surface。

#### J7 打开等待区/控制任务：我要知道现在发生什么，不能被旧状态误导

从冷打开、断线恢复、任务持续运行到任务终态，用户看到的控制状态都需要后端当前事实或完整性证据。
缓存历史用于阅读，展示偏好用于展开，二者都不能制造“现在仍在排队”的结论。
未知/过期/current可区分；按钮可用性服从权限与新鲜度，而非缓存里是否有一个request。
状态更新不移动阅读视窗，不重置用户展开偏好。

#### 场景的完成责任

每个场景都要检查：触发是否覆盖所有入口 → 义务是否真正建立 → 异步推进是否可能静默中断 →
失败/取消/恢复是否有终态 → 用户继续操作是否优先 → 可见结果是否符合目的。
故障原句只用于举证和回归定位；场景模型必须能推导用户未报告的失败，例如Meta超时后永久不追新、
同频道重复进入被错误合并、浏览历史时停止接收最新消息。

### 1.9 外部驱动模型：用户没有操作，系统也会变化

用户场景定义系统要完成的目的；后端、网络、浏览器、存储和渲染器同样是主动事件源。
不能把后者全归入一个“后台更新”回调，再让其自行修改任何状态。
以下是第1.4节事件族的具体合同，不是新增一批独立控制器。

| 主动来源 | 可以真实发生的变化 | 接受/失效边界及唯一责任 | 对阅读、输入和画面的影响规则 |
|---|---|---|---|
| 后端消息/任务 | 新消息、流式修订、终态、编辑/撤回、父子关系补齐、成员资料变化 | Replica按消息/修订身份合流；ControlProjection按完整性证据确定当前状态；Presentation派生受影响内容 | 后端可以改变正文事实，不能决定本地展开/阅读目标；头像/名字更新也计入内容几何，不能绕过列表合同 |
| 后端会话/权限 | 服务重启、重新attach、频道删除、成员权限变化、资源失效 | SyncSession判断连接世代；实际数据世界身份决定缓存可否复用；Access状态约束所有迟到答复 | 重连不是新视图；权限撤销可以终止显示，优先于保位，但不能以普通超时伪造撤权/空频道 |
| 传输与服务响应 | 延迟、乱序、重复、断连、半开连接、拒绝/限流、页只到一部分、响应schema不兼容 | 请求ID/连接generation/数据身份分别校验；每请求有终态、超时、错误和取消语义；Scheduler拥有重试预算 | 不等下一push救活追赶，不因失败清空已读内容；畸形/不完整批次不得推进coverage或伪报exhausted |
| 本地持久化 | IndexedDB升级被其他tab阻塞、读取慢、quota失败、事务中止、缓存被回收、旧书签晚到 | Storage/Replica保证消息与coverage原子性；会话状态有版本；失败进入相应存储状态，不冒充hydrate成功 | 存储失败不停止可用live；未持久的内容不能宣称可安全resume；本地发送未接受不能清稿 |
| 浏览器/操作系统 | 手机软键盘、方向/缩放/系统字体变化、动态地址栏、安全区、冻结/恢复、BFCache、内存压力 | Surface管理外框；MessageList管理内部测量；Session管理激活和恢复；BFCache恢复也重新校准网络新鲜度 | 变化可导致合法重排，但不生成“回最新”；隐藏/0尺寸是暂不可测，不是空消息或可覆盖旧书签的有效测量 |
| 异步资源/渲染任务 | 图片/字体/附件下载、图表/高亮/Markdown计算完成或失败，旧任务晚于新revision完成 | 结果携带messageID/contentRevision及适用布局参数；Content层只接受仍适用的结果，列表拥有测量 | 旧正文计算结果不能覆盖新正文；旧宽度测量不可复用为当前几何；单条失败局部降级而非清空全窗 |
| React/DOM | 渲染被打断/重放、effect重复安装、回收、ResizeObserver通知、程序滚动产生scroll事件、原生焦点滚动 | 已提交版本才有副作用；订阅/命令消费幂等；实际程序性位置变化仍归MessageList，焦点入口受控 | 未提交render不得消费导航或发网络命令；scroll通知本身不等于用户操作；补偿不能再次触发业务导航 |
| 其他页面/设备与时钟 | 其他tab写书签/退出账号、另一个设备标已读、系统时间跳变 | 账号失效按共享权限处理；草稿/书签用版本冲突策略；远端read frontier与本地阅读目标分开；超时用单调时钟 | 另一个设备标已读不把本页面滚走；旧tab不覆盖当前稿件；不能按客户端时间决定消息顺序或任务是否终态 |

#### 必须成立的跨来源裁决

1. 身份/权限失效优先于显示保持；普通网络失败不等于身份失效。服务boot变化本身也不能擅自证明账本被重置，
   应使用协议定义的数据世界标识/连续性证据；若协议无法证明，走明确重新校准，而非盲信缓存或重置UI。
2. 事实接收、持久化、展示提交各有进度。内存已收到≠已持久化≠用户已读；checkpoint须遵守其协议定义，
   不能把网络端的到达通知当作本地写入成功证明。
3. 每项异步任务绑定其实际依赖版本：数据任务查dataEpoch/请求身份，正文任务查contentRevision，
   测量查layoutRevision，导航另查activation/inputEpoch。不能用一个generation大开关把所有进度清零。
4. 正文计算完成与DOM测量完成只提交结果/观测，无导航权；当前版本已变时丢掉过期结果并保留新任务义务。
5. 用户连续操作与后台事实必须共同前进：不能用永久暂停live、历史或控制状态来证明画面不跳。
   有限设备预算下允许调度、合并和局部失败，但不能静默饿死一个仍有效的用户需求。
6. 追赶针对已取得的有限目标head H完成一次证明；持续live可提高后续目标，不能让“追平无限移动的最新”
   成为永远不显示内容或永远不给出状态的屏障。ControlProjection的完整性不借用这个head证明替代。
7. 后台/冻结的计时器恢复后合并为一次当前校准，不补跑每个过期tick；用户时钟调整不能导致瞬时重试风暴。

#### 不用用户动作也能打破设计的反例

- 页面静止，旧缓存在live终态后到达：必须保留终态，不让旧queued复活、不重挂全窗。
- 页面静止，字体/图片晚到：没有用户scroll也会变高，仍须通过唯一几何执行器处理。
- 网络保持open却没有有效feed，head已经前进：仍须发现缺口，连接布尔值不能关闭新鲜度义务。
- 组件隐藏时测得0高，返回后内容仍存在：不能保存0尺寸快照覆盖有效书签或把列表当作空。
- 另一个tab完成数据库升级或写入较旧书签：恢复不得覆盖本次已提交输入/阅读状态。

这些反例分别落在对应owner，不允许把跨来源问题全部塞进滚动hook处理。

## 2. 已核实的问题，不再泛称“抖动原因”

1. 旧 Virtuoso 接入同时使用其 prepend 补偿与 `restorePrependAnchor` 手写像素修正。
   同一几何存在两个执行者；恢复那个版本不是解决方案。
2. `45c1054` 改成自写 `MeasuredTimeline`。当前未提交版本继续把准入、测高、回收、
   输入前置渲染和定位集中于该组件，实际上开始维护一个新的虚拟列表引擎。
3. `conversation-viewport.js` 的同一 mode 同时包含 following/browsing/loading-before/restoring；
   Hook 又通过 `followsTailRef` 表达另一份跟随状态。加载过程和用户阅读意图仍纠缠。
4. `rowID + offset` 只表示行边界锚点。同一长消息内部段落重排时，行顶不动不等于正在读的段落不动。
5. 当前 `projectTimeline` 仍扫描时间线。稳定 React key 不等于解析、投影与主线程工作已经增量化。
6. 既有测试包含静态/合成场景和模拟尺寸；不能把它们通过写成真实滚动及完整数据链路合格。

这些是代码中的结构事实，不表示已经复现并解释了用户每一次小抖动。

## 3. 技术选择：恢复成熟组件职责，不恢复旧接法

R2技术路线：以项目已安装的 `react-virtuoso@4.18.12` 为基础引擎，保留其尺寸树、测量、虚拟窗口和DOM渲染；
MessageList的业务接入保持薄层。现有公开API不足以覆盖全部目标，因此不能再声称“原包加几个props即可完成”。
第15.4节将缺失能力定义为**列表组件内部的事务扩展**，而不是业务Hook里的第二个几何控制器。
这是一个需要受控维护的库扩展设计，不是假称原版已经支持；不是继续使用自写MeasuredTimeline。
本轮只作设计，不修改node_modules、不下载源码、不引入商业产品。实施必须从可追溯、保留许可的上游源码构建扩展，
禁止修改压缩产物或复制整套库后失去上游版本关系。此路线的复杂度和维护责任计入组件工作包，不能藏进“薄适配”。
本地类型定义确认存在 `firstItemIndex`、`followOutput`、`computeItemKey`、
`increaseViewportBy`、`minOverscanItemCount`、`getState` 等接口；不凭最新网站猜旧版本能力。

组件承担：尺寸观测、虚拟窗口、DOM 回收、统一事务保位、底部跟随执行。
应用承担：稳定展示数据、操作语义、阅读意图与导航授权。
应用不得同时维护另一份权威尺寸树、手动 spacer 和像素补偿。

官方文档支持变高列表、prepend 与跟随配置，但**不证明本项目的所有组合已经可靠**。
库内部有 rAF/多次测量也不是自行重写它的充分依据；验收看屏幕上的结果。

专用 `@virtuoso.dev/message-list` 的数据与滚动语义绑定方式可作为契约参考；
它是独立的商业授权产品，不是现有依赖中的组件。本方案不擅自引入或购买。
扩展采用事务模式时必须替换引擎内旧的定位/补偿入口，而不是和它们并行运行。
若源码接入证明无法在限定的组件边界兑现第15.4节，停止该组件实现并重新作技术选型，
不得把“组件模式已设计”写成“组件运行已经合格”，也不得退回业务侧无限补偿。

## 4. 唯一状态来源

| 模型 | 持有的事实 | 明确不持有 |
|---|---|---|
| ChannelReplica（保留） | 按身份/seq 合流的账本、coverage、epoch | scrollTop、行高、折叠、阅读模式 |
| ConversationPresentation | 稳定消息/内容块身份、顺序、内容 revision、展示变更 | 网络操作、滚动位置、任务是否仍在运行的独立副本 |
| PresentationChoices | 用户主动的展开/收起、图表模式等选择 | queued/running 等后端运行状态 |
| ReadingSession | following/browsing、语义书签、未读尾部、导航令牌、输入 epoch | 历史加载状态、尺寸表、补偿计时器 |
| HistoryDemand | 用户所需语义范围、请求状态、exhausted/error | 当前阅读目标、定位命令 |
| MessageList 内部状态 | 组件自己的测量、物化范围、补偿执行 | 账本、跨频道业务状态 |

ReadingSession 的稳定 mode 只有 `following | browsing`。
`history: idle | loading | exhausted | error`、`navigation: idle | pending` 是独立状态，
不能通过“历史完成”把浏览用户转为 restoring/following。
界面和执行层读取同一 ReadingSession 快照，不再靠 mode 与 followsTailRef 两份状态互补。

频道会话按 principal + channel + view identity 隔离；切频道保存语义书签。
尺寸快照只作为组件私有的可丢弃缓存，不能代替书签，也不能覆盖 following 意图。
首屏无书签才默认尾部；恢复失败留在可用的相邻内容并提示，不静默跳到最新。

## 5. React 组件合同

```text
ConversationScreen
  ├─ MessageViewport（Surface拥有边界，唯一消息滚动容器）
  │    └─ MessageList（成熟虚拟列表 + 薄适配）
  │         └─ MessageItem / ContentBlock（稳定身份、局部订阅）
  └─ ComposerStack（独立悬浮层）
       ├─ WaitingArea（贴着 Composer 顶部）
       ├─ Composer（输入、回复、附件自然增高）
       └─ StatusBar（固定占位，只换文案）
```

- ConversationScreen 组装数据与用户动作，不测高、不定位、不按缓存/网络状态重新 key 整个会话。
- MessageViewport 的几何边界由Surface根据可视视口和用户内容占用确定，输入栈上方保留32px。
  它不是列表数据的派生状态，历史loading/网络/任务状态不增减消息区高度；容器变化进入统一保位事务。
- MessageList 只接收展示快照和更新语义。只有它接入虚拟列表公开 API；不请求网络。
  它报告阅读范围、尾部几何、锚点观察和用户输入，不自行创造业务导航。
- MessageItem/ContentBlock 不滚动祖先、不读取连接状态来决定高度；组件类型/key 不因滚动重建。
- WaitingArea 继续来自已校准的后端事实，用户展开选择可以本地保存，任务运行状态不能恢复自旧 UI 缓存。
- ComposerStack 的用户内容增长允许Surface调整可用阅读高度，等待区随输入框顶部移动；状态文案不推动Composer。
  这项范围修订已获用户明确同意；不改变默认展开和样式，不借此为后台状态创建布局通道。

数据流：Replica → Presentation → ListUpdate → MessageList。
控制流：用户动作 → ReadingSession → 被授权的 ListUpdate/Navigation。
反馈流：MessageList 的观察 → 书签/未读/HistoryDemand；**观察不是新的定位命令**。

### 5.1 相邻 Surface 不回归：补齐真实反馈遗漏

- MobileNavigationSurface 与 ConversationScreen 是独立页面边界；隐藏的会话不参与目录布局、点击命中或焦点。
  网络订阅可继续更新模型，但不能把隐藏工作区的Grid/高度变量施加给目录。
- Header保留既有移动紧凑布局；高度/断点/token由Header自身合同决定，不继承消息区或输入栈动态几何。
- PreviewSurface按实际可视宽度布局，根容器 `min-width`/固定桌面宽度不能撑出手机；
  超宽代码/表格/媒体的溢出局限于其内容容器，不使整页不可用。关闭Preview通过统一会话恢复，不重置消息列表。
- FilePreview的unsupported/error态与预览成功态一样保留文件身份/可访问下载入口；
  权限失效显示真实错误，不以“无法预览”移除所有操作，也不构造越权下载。
- Composer输入订阅必须与消息高频变更隔离：打字/输入法状态更新不调用全量Presentation，
  live/history也不得迫使编辑器重挂或重设selection。输入延迟单独验收，消息滚动顺畅不等于输入及时。
- 等待区默认展开和原外观是需保留的既有行为，不以空间优化名义默认收起。
  展开选择与任务状态分离；状态未知不能假装空队列，不能靠隐藏控件规避G5。
- 展开后收起不只是Choices正确：组件必须使旧占位失效并恢复真实可滚范围，
  避免大片空白、滚不动或倒退；该合同由E04独立验收，不能由“展开后再返回仍展开”替代。

这些是现有功能的责任收口，不授权重新设计页面样式；具体修改仅在完整接入和验收时按owner实施。

## 6. 不是传一个 rows 数组：明确列表更新协议

Presentation 输出不可变展示快照，不能让旧 row 对象的 getter 随可变账本偷偷改变内容。
同一 `(itemID, contentRevision, choicesRevision)` 必须对应同一呈现输入；未变项保留对象身份。
每条数据更新先分类；提交时再与当前 ReadingSession 合成一个 ListCommit。
数据准备本身不得保存有执行权限的尾随决策：

```ts
type ListUpdate = {
  dataEpoch: string;      // 数据世界身份，不是 socket generation
  activationID: string;
  viewID: string;         // scope/filter，不由消息数量生成
  baseRevision: number;
  nextRevision: number;
  items: readonly PresentationItem[];
  changes: readonly ListChange[];
};

type ListChange =
  | { kind: 'insert'; beforeID: string | null; ids: readonly string[] }
  | { kind: 'revise'; ids: readonly string[] }
  | { kind: 'remove'; ids: readonly string[] }
  | { kind: 'rebase'; reason: 'initialize' | 'user-view-change' | 'authoritative-reset' };

type ListCommit = {
  update: ListUpdate;
  readingRevision: number;
  inputEpoch: number;
  policy: 'preserve' | 'follow' | 'explicit-navigation';
  navigationID?: string;
};

type Navigation = {
  id: string;
  dataEpoch: string;
  activationID: string;
  viewID: string;
  inputEpoch: number;
  target: 'latest' | { messageID: string; blockID?: string; offset: number };
  reason: 'open-session' | 'return-session' | 'user-jump' | 'user-filter';
};
```

这是产品侧的协议，不是声称 Virtuoso 原生接受这些字段。R2组件事务扩展接收该协议，业务薄层不执行像素补偿。
定位命令与普通 ListUpdate 分离；history/page_end/cache/measurement 没有 Navigation 构造权。
更新必须匹配当前 epoch 和 baseRevision；乱序旧更新丢弃或由 Presentation 基于当前版本重算，不能拿旧数组覆盖新视图。
去重、prepend + append 同时发生、流式更新与历史并发，都由同一串行展示 reducer 生成下一版本，不能各自 setRows。
ListCommit 是同步提交边界的逻辑合同，不是可以在队列中滞留后无条件执行的命令。
React 调度/异步准备跨越用户操作时必须重取阅读策略；匹配版本的数据继续应用，旧 follow 授权不能继续执行。
`revise` 不改变 identity/order；正文替换属于内容 revision，位置不变的前提不等于高度不变。
物理重排既有消息不属于普通数据合流；若权威更正确实要求重排，必须显式标识其身份变更及保位义务，不能伪装用户导航。

| 操作 | 必须满足的前提 | 组件接入及禁止行为 |
|---|---|---|
| initialize | 新会话，初始目标已经选定 | 首次定位参数一次性提交；等待首个可用窗口期间不能先露出错误位置再跳走 |
| prepend | 旧 item 的身份和相对顺序完整保留，新前缀 count 明确 | 作为insert变更进入15.4统一事务；不同时启动旧firstItemIndex/deviation补偿 |
| append | 只向尾部增加身份，旧项不重分组 | 提交当刻following才允许尾随；关闭原有独立followOutput调度，未读增加不产生导航 |
| update | 身份不变，受影响项 revision 明确 | 仅更新对应消息/块，由组件统一测量；不能重新初始化列表或切换默认折叠 |
| rebase | 用户切筛选/视图，或明确的权威数据世界重置 | 区分用户导航与后台失效；删除单个锚点不触发 rebase，普通同步/补齐父线程也不得伪装成 rebase |

上表仅是变更集合的简单特例。中间insert/remove/同时revise/权威reset统一进入15.4的身份重映射事务；
不能再套用通用Virtuoso纯prepend条件。扩展的实际实现与真实浏览器验证尚未完成。
删除一个锚点只触发第 1.5 节的确定性替代，不自动 rebase 或取得用户导航权限。
rebase 不等于 remount，也不天然允许跳到最新。只有用户改变视图产生有来源的导航；
后台 authoritative-reset 保留可解释的语义书签或明确失效状态，不能借重置伪造用户意图。

`firstItemIndex` 是原通用组件的索引映射，不是seq，也不是业务阅读位置。
R2事务模式由组件内部统一映射稳定身份；业务层不再自行维护该字段触发另一补偿路径。
同一个 view 内不得因网络 boot、缓存 ready、条目数变化重新 key MessageList。
事务模式下原有独立followOutput/scrollIntoViewOnChange/自动scrollToIndex路径关闭，
不是“函数返回false但其他回调仍钉底”。尾随与保位只有15.4同一执行入口。

### 阅读状态机

- 初次无有效会话记录进入频道：following；已有记录时以保存的 mode 为权威。
  保存为 following 即使附有旧 anchor 也只恢复尾部；保存为 browsing 才解析书签并进行一次恢复。
  每次 activation 的初始目标只决策一次；首批/后续批次不会重复初始化，用户接管后取消迟到恢复。
- 用户向上滚动/浏览内容：browsing，同时增加 inputEpoch，使未发出的旧导航失效。
- 用户点击回到最新：following + 一次显式导航。
- 用户主动向下到达尾端：必须同时有可归因的用户滚动与尾部观察，才可转 following。
   仅有 atBottom=true、内容缩短、viewport resize、历史结束都无此权限。
  归因必须属于同一次有效主列表操作和相容的布局版本，不用持久 arm 布尔值等待未来某个 atBottom。
- 历史开始/完成/失败、Meta、缓存、水合、live：保持阅读 mode；只更新各自状态。
- 显式导航按 id 消费一次。异步查找目标返回时重新校验 epoch/inputEpoch；用户已操作则取消。

不把“反复调用直到定位成功”作为可靠性手段。库已经接收的定位是否会迟到重试，
需要在组件边界验证；当前公开接口未提供通用取消令牌，不能把应用令牌当成能取消库内部工作的证明。
若库会在用户接管后继续强制定位，这就是组件能力门槛失败，不能用反向 scrollTop 抵消。

## 7. 历史、数据和视觉之间的边界

历史调度提前维持当前阅读范围前方的可用数据，不等到真正触顶才发请求。
已有 HistoryScheduler/Replica 保留；会话向它表达持续范围需求，取消的是过期需求，不是当前阅读位置。
有限接口表达 `channel/view + anchor/range + intent + urgency/deadline + demandID`，
由Scheduler选择来源、批次、并发、重试和预算；UI不能另设调度队列或“继续拉一段直到出现可见消息”的循环。
“不在UI拉取”不等于不拉历史，也不等于用户必须等到触顶才开始准备。
未知数据、网络失败、真正耗尽分别表示；只有有证据的exhausted才能关闭继续向前需求。

完整链路：

```text
用户接近已知历史边缘
  → 更新 HistoryDemand（语义锚点、范围、紧迫度）
  → Scheduler 选择本地/远端并合流
  → Replica 提交带 epoch/revision 的完整批次
  → Presentation 生成稳定前缀、去重并分类
  → ListUpdate(实际变更集合，通常为前缀插入)
  → 提交时依据当前 ReadingSession 选择 preserve/follow
  → MessageList 保持当前阅读内容或当前尾随意图；历史回调不创造导航
```

请求开始时不保存一个稍后要恢复的屏幕位置。网络等待期间用户走到哪里，
就在数据提交当刻保住那里。请求完成没有 `restore()/latest()/focus()` 调用路径。
同一页即使重复返回也不增加列表版本或重复减少 firstItemIndex。
exhausted 是数据范围的稳定事实，不能因顶部几何回调反复触发重新加载。

“有数据”与“有足够可渲染内容”分开：后台可提前准备正文 AST、稳定内容块、媒体尺寸，
但不另造隐藏 DOM 测量引擎。实际尺寸与 DOM 物化由列表组件独占。
无数据时保留当前窗口及锚点，加载提示放在不改变流内高度的位置；不能先清空内容。

组件预渲染预算通过公开配置表达，并按设备成本确定有界预算，不在每个 wheel 中强制挂载大批富文本。
滚动输入路径不解析整篇 Markdown、不扫描全账本、不 flushSync 完成大量 DOM 准备。
快速滚动不启用整屏空白占位替换现有消息；不能把滚动事件之后才挂载内容作为唯一供给机制。

## 8. 内容模型：长消息不能只看外框

仅把一整篇长文当成一个会变化的黑盒行，无法证明段落位置稳定。
Presentation 需要可识别的内容结构：messageID + blockID；块身份不能使用全列表数组下标。
长文本、代码、媒体、线程与过程区按语义内容组织，但这不等于每块都必须成为虚拟列表 item。
默认以稳定消息实体接入列表；把块提升为 item 会引入中间插入、分组、选择和焦点合同，
没有明确收益和完整能力映射前不做这项扩张。块内语义锚点由第15.4节统一几何事务处理，
仍须实施与验证，不能在MessageItem中另外写scrollTop。

- 已完成块复用 AST/React 输入；stream 只更新未完成块并追加新块，不能每 token 重建整条消息。
- 文本解析可能回改前文（未闭合 Markdown、终态全文替换）。不能假设 stream 永远是 append。
  所有更新仍按最新事实呈现；撤回“默认冻结正文、让用户手动接受更新”的方案，它未经产品授权。
  存活且未改写的阅读内容应保位；正在阅读的文字本身被修改/删除时，保留最近有效语义位置，
  不可能证明被删除的文字仍保持原屏幕坐标。R2第15.3/15.4节规定块匹配、语义降级与组件内事务；
  这是设计机制，任意Markdown重写下的实际行为仍必须经过组件验收，不能标成运行已解决。
- 不同消息的历史插入和新消息 append 不得被某条消息的正文准备阻塞。
- 折叠、详情、线程和图表模式来自 PresentationChoices；DOM 回收与 latest 身份变化不改选择。
- 日期/作者头/线程归属一经呈现，普通历史补齐不得把旧内容搬到另一棵树。
  新父关系更新语义索引，不把已显示子消息突然塞回父线程；需要重组的视图通过明确 rebase 进入。
- 媒体框尺寸先于解码确定；字体策略避免后台换字形引发已显示正文重新换行。
  对无法满足稳定尺寸的嵌入内容，不能承诺无位移，必须有稳定容器或显式打开方式。
- 内容 margin 必须封闭在被库测量的 item 内；高度动画、异步 autoFocus、scrollIntoView 不得藏在正文组件里。

必须直说的边界：正在读的文本本身被删除、用户改变窗口宽度、用户主动收起当前内容时，
不可能同时保持原文本与每个像素位置不变。此类属于显式内容/环境改变，按保留同语义块或最近存活邻项处理，
不能偷偷回到底部。普通 history/live/cache 更新不属于这个例外。

## 9. 同步与控制状态接口：不能让旧故障换个入口回来

本节是会话组件的输入合同与数据层后续验收义务，不声称本次视觉接入已经修复所有同步缺口。

### 9.1 当前频道的新鲜度

- 进入/重新选择频道、回前台、显式回到最新或重试等表达当前频道兴趣的动作，立即发起轻量 Meta 校准。
- 相同 in-flight 请求可合并，不能把 stale cache 当成这次服务端校准的答复；失败有明确状态与重试路径。
- Meta/control 优先，不排在大量历史反序列化后。Meta 到达不发导航，也不更换 MessageList 的 identity。
- 服务端 head 表示已知目标，不表示本地已经具备中间所有事实。比较的是已证明的 coverage，而不是 max(seq)。
- 缺口由高优先级 catch-up 补齐；阅读历史的 cursor 与最新追赶的 cursor 分开。push、catch-up、缓存幂等合流。
- 相应 epoch/channel 不匹配的迟到答复不改变当前频道和优先级。
- 连接、attach、缓存恢复、历史与追赶状态独立；缓存慢不关闭已经可用的实时路径。

### 9.2 等待区

权威是后端当前任务事实。显示历史内容的缓存，不等于具备当前队列状态的证据。
`没有读到 terminal` 不能推出 `仍然 queued`；仅覆盖尾部/head 也不必然证明所有旧任务的状态完整。

ControlProjection 只有两类可接受输入：

1. 后端带版本/epoch 的当前控制快照，并接续该版本之后的增量；或
2. 有明确完整性证明的任务生命周期投影，能证明相关任务的状态已追到权威边界。

断线或缺口时结果是 `unknown/stale`，不能把上次缓存的 queued 当作新鲜结论，也不能伪装成后端空队列。
过渡展示必须明确，不能改变等待区默认展开偏好或推动消息视窗。
本地未发送意图与后端队列分开命名、分开来源，不冒充服务端已接收。

当前控制 API 能否提供上述完整性，实施时必须核实；若没有，需要明确的后端接口工作，
不能用前端延时隐藏、清 localStorage、年龄阈值或再加一个 readiness boolean 假装解决。

### 9.3 独立工作包，不是整体完成豁免

完整 local-first Outbox、跨设备阅读前沿、持久草稿和后端 Meta 启动性能是独立工作包。
它们不是视觉适配器的职责，但属于相应端到端用户场景的交付依赖；不能以不在视觉包为由忽略审核 A05–A09。
它们不得驱动视觉定位；也不能因为本轮视窗替换完成就被一并标成已解决。
发送本地接受、receipt、feed 必须对应同一稳定消息身份，不因确认过程重复新增气泡或改变其视觉归属。

## 10. 不变量与证明义务

定义：

- D：消息事实与同步进度。
- P：已提交的展示版本（稳定 item/block 身份）。
- R：阅读意图与导航权限。
- G：列表组件拥有的尺寸、物化与坐标状态。
- U：用户输入/明确路由动作。
- 对未被用户改变、且仍存活的阅读块 a，`Y(a)` 是它相对视窗的屏幕坐标。

目标不是承诺任意浏览器、任意长任务中永远零帧延迟，而是消除已知越权路径，
并将可见稳定性明确列为组件必须通过的实现契约。

| 编号 | 不变量 | 由谁保证 | 证明/验证方法 |
|---|---|---|---|
| I1 阅读权威 | 非 U 的后台事件不能改变 R 的 mode/目标 | ReadingSession reducer | 事件集合分离；枚举与随机排列 history/live/cache/resize，R 的阅读目标保持不变 |
| I2 导航权限 | 每次导航都有来源、epoch、inputEpoch、id；迟到旧命令不可执行 | ReadingSession + 薄适配 | 构造权受模块边界限制；用户接管前后插入异步完成，旧令牌被拒绝 |
| I3 单一几何执行 | 除列表组件外无程序性消息区定位、行高表、补偿循环 | MessageList 边界 | 静态依赖/调用检查与运行期来源记录；浏览器原生用户滚动不受此禁止 |
| I4 数据一致提交 | 每次展示更新只应用一次、版本连续、数据与操作类型一致 | Presentation reducer | 重复/乱序/混合更新性质测试；纯 prepend 后旧身份序列完整保留 |
| I5 可见锚点 | browsing 且锚点存活、几何可行时背景更新满足 Y'(a)=Y(a)，允许测量量化误差但不允许累积漂移 | MessageList + ContentBlock | 依赖 I4 和稳定内容块合同；真实浏览器逐帧测同一内容块/文字；删除/范围缩短按显式降级合同验证 |
| I6 手势连续 | 后台提交不覆盖用户已产生的运动、不重放请求时的锚点 | MessageList 接入 | 在请求中途持续滚动/反向，比较原生轨迹；库已接收导航的取消能力也必须验证 |
| I7 身份与选择稳定 | prepend/latest变化/DOM回收不改变旧项归属和用户展示选择 | Presentation + Choices | 结构序列与展开状态的组合测试；同 revision 不允许偷变内容 |
| I8 控制新鲜度 | 无完整性依据的旧 queued 不得表示当前后端状态 | ControlProjection | 缺 terminal、跨 epoch、缓存晚到、快照/增量竞态反例 |
| I9 容器隔离 | 网络、历史、等待区状态不改变消息区边界及移动导航布局 | Screen/Viewport/ComposerStack | 在相同窗口/输入内容下遍历状态，比较边界、层级和点击目标 |
| I10 有界供给 | 准备不会造成全列表挂载或逐 token 全量解析；目标负载内无可见空窗 | Presentation + MessageList | 测解析/提交成本、DOM 数量与逐帧实际覆盖；单看 overscan 值不算证明 |

### 归纳证明：后台事件不能劫持阅读位置

初态：由新会话/书签明确建立 R。
归纳步：在阅读内容仍存活的前提下，所有后台事件只更新 D、P 或组件内部 G；它们没有改变 R 或构造 Navigation 的权限。
因此任意长的后台事件序列都不能在应用模型中把 browsing 变成 following 或指定另一阅读目标。
用户事件是改变 R 阅读目标的正常入口；内容删除使锚点失效属于第 8 节明确例外，不能据此自动进入 following。
旧 epoch 的事件被拒绝，所以迟到历史也不能突破这个结论。

该证明只涵盖**语义控制权**。还需组件实现 I5/I6，才能从“目标没变”推出“屏幕没跳”。
不能从 I1/I3 自动推出 I5，正是前面“一个写入点即完成”的逻辑错误。

### 几何稳定性的条件证明

对于存活的稳定内容块 a，旧布局位置为 H(a)，视窗坐标为 H(a)-scrollTop。
prepend 或上方 resize 后，由唯一布局组件补偿 `ΔscrollTop = ΔH(a)`，故 Y'(a)=Y(a)。
下方 append 的 ΔH(a)=0，browsing 下也不尾随，所以不需改变视窗坐标。
following 下目标就是尾端，不采用保留 a 的约束。

前提必须明确：内容块身份存活、块内部内容未被后台重排、同一布局版本、补偿与用户运动不相互覆盖。
另一个必要前提是理想新 scrollTop 处于新文档合法范围
`[0, max(0, scrollHeight-clientHeight)]`。删除大量内容、内容缩短或视窗增高时可能不成立。
此时只能按确定性邻项及合法范围钳制，保持 browsing；不得反复补偿振荡、伪造 following 或偷偷增加无限占位。
诊断需区分这种不可避免的范围钳制与没有合法原因的阅读跳转。
这些分别由 Presentation、稳定内容结构、ListUpdate 和组件手势合同承担。
任意正文改写不满足“块内部未重排”的前提；该例外需独立的语义锚点降级合同，不能由此推导绝对像素不变。
如果组件在绘制之间暴露错误坐标，证明的实现前提不成立，应判为组件门槛失败；不能补一个第二执行者。

### 空白帧不是可无条件证明不存在的性质

网络没有返回的数据不可能提前显示，浏览器主线程无限阻塞时也无法保证任意速度不露白。
可保证的是：不清空已显示内容、不把未准备的整屏占位冒充已完成消息、不在手势路径做重工作；
并在明确设备与内容负载下验证物化预算和逐帧覆盖。网络等待与已有数据渲染不及必须分开记录。
零现象承诺如果没有这些前提，只是另一句未经验证的“彻底修复”。

## 11. 已报告问题逐项归属

这里的“排除条件”是新架构的设计/验收义务，不是当前代码已修复声明。
对尚未在真实路径复现的闪动，不强行指定一个已证实的单一根因。

| 历史问题 | 破坏的边界或需要排查的条件 | 责任 owner / 排除条件 |
|---|---|---|
| 冷启动/强刷后 prepend 闪动、跳位 | 数据注入带动重置、索引不一致或双重补偿；组件测量也需核实 | Presentation + MessageList，I3/I4/I5；异构冷行逐帧检验 |
| 触顶加载结束后跳回先前位置 | 请求时锚点被当作提交时位置，或完成触发 restore | HistoryDemand 不输出导航；I1/I2/I6 |
| 请求期间继续滑动却被拉回 | 迟到回调覆盖用户输入 | inputEpoch 拒绝旧命令；组件不得重放已被用户接管的定位 |
| 快速滑动先白屏再有内容 | 数据不足、主线程阻塞或 DOM 供给不足必须分别诊断 | I10；保留现有窗口、增量正文准备、库内有界物化，不加自写手势引擎 |
| live 到达拉走历史阅读位置 | 几何 atBottom 被当作跟随意图，或重复自动尾随 | ReadingSession 显式授权；browsing 实际关闭 follow；I1/I3 |
| 最后一条长文随后自动收起 | latest 身份决定了展开策略 | Choices 是唯一选择来源；latest 不决定高度；I7 |
| 长文中段仍轻微跳动 | 只保消息外框、全文重解析或块内异步重排 | 稳定内容结构及块内语义锚点；I5/I7，任意重写能力尚未闭合，不靠冻结更新回避 |
| 回收后线程/过程/Mermaid 折叠变化 | 用户选择错误保存在临时 DOM 组件里 | Choices 按稳定业务身份保留，不缓存后端控制状态 |
| 展开/收起后空白或定位变化 | 无效尺寸、多个 resize 修正、零高 item | 内容统一测量合同；用户动作退出跟随；无高度动画和第二补偿者 |
| 日期、头像消失；子请求突然移入父线程 | 补齐历史改写已展示拓扑 | 稳定投影；普通 prepend 不重组旧项，显式 rebase 才能换语义视图 |
| 切频道回来落在中间而不是底部 | 物理快照覆盖 following；旧频道导航迟到 | ReadingSession 权威 + epoch；following 禁用旧位置恢复 |
| 筛选/Preview 返回重复跳转 | 视图变更与普通数据更新混用 | view identity 与导航令牌；恢复一次，用户输入取消 |
| 断线提示把 Composer 向上推 | 状态内容改变外部几何 | 固定 StatusBar；I9，不用隐藏/显示改变占位 |
| 输入/回复变高，等待区却不贴顶部 | 等待区被固定到页面而非 ComposerStack | 等待区与Composer同栈，用户内容尺寸经Surface统一分配阅读高度，状态不触发尺寸更新 |
| 消息透到输入框背后、底部按钮不能点 | 阅读边界与浮层实际占用不一致 | 实际输入栈上沿+32px间距，真实视窗裁剪；点击命中与末项可见验收，不拿Footer假留白代替 |
| 移动频道列表布局被会话影响 | 导航 Surface 与隐藏工作区共享几何 | 导航独立容器；会话无权修改其尺寸/显示策略 |
| 移动打开/切频道最新消息慢，等下一条 push 才更新 | 兴趣动作没有触发新鲜度校准、错误相信本地最大 seq | Meta → coverage → catch-up 独立合同；不能拿重定位/重挂列表当同步 |
| 已连接却像离线，等待缓存/历史 | transport、attach、hydrate/history 串成成功条件 | SyncSession 独立状态；I1/I9 保证其变化不碰阅读位置 |
| 等候区恢复过期 queued | 缓存/不完整生命周期被当作当前控制权威 | ControlProjection 的完整性证据；I8，缺证据就是 unknown，不猜 current |
| 历史补齐覆盖 live、旧账号状态串入 | 合流版本/epoch/coverage 错误 | Replica/SyncSession；I4/I8，视图不能修补数据事实 |
| 发送 receipt/local echo 重复或跳位 | 提交身份和账本身份没有稳定映射 | Submission/Presentation 合同；完整 Outbox 另包，不能虚称本轮完成 |
| 文件不能预览且没有下载入口 | 文件面板能力降级不完整 | FilePreview：保留现有下载能力；与消息滚动无依赖，不因本轮替换删除 |

### 出问题时如何确定归属

按同一 updateID/epoch 记录最少必要的元数据，不记录消息正文：
数据版本 → 展示版本与操作类型 → 阅读策略/导航来源 → 组件提交与可见锚点偏差。
诊断有界、按需启用，不在每帧无限刷日志。

1. Replica 已错/缺事实：归数据同步；禁止视觉层伪造终态或按时间猜 queued。
2. Replica 正确但 item 身份/顺序/revision 错：归 Presentation；禁止调 scrollTop 掩盖。
3. 数据只 prepend，但生成了导航或 changing mode：归 ReadingSession/协调协议。
4. update 和策略正确，item 稳定，组件仍改变 Y(a)：归 MessageList 接入/组件实现，保留最小复现。
5. 行外锚点稳定而阅读段落移动：归 ContentBlock 的重排/版本合同，不继续改历史阈值。
6. 组件区域边界变化或被遮挡：归 Surface/样式所有权，不改虚拟列表补偿。

## 12. 替换计划：迁移机制，不拆文件交差

### A. 先建立模型和合同

建立 ReadingSession reducer、稳定 Presentation/ContentBlock、ListUpdate reducer；
把 history/navigation/loading 的状态从阅读 mode 中移出。
保持已有业务行为与同步输入，不在此时改网络协议或外观。
每个旧回调必须归到一个新 owner，找不到归属就不能保留成逃生分支。

## 14. 当前方案的明确取舍

- 采用成熟列表引擎作为唯一几何执行者；不继续投资自写引擎。R2明确选择受控的组件内部事务扩展，不能宣称原版已具备缺失能力；扩展仍须实现与验收。
- 应用保留自己的业务展示模型与阅读规则，而不是期待一个组件理解账本、线程和后端任务语义。
- 不默认冻结正文或增加“手动接受更新”。区分未改变的阅读内容与内容本身被编辑/删除；后者采用语义邻项降级，块内定位按15.3/15.4实施并验证。
- 保留现有ComposerStack外观；按用户确认允许用户内容增长调整阅读高度，网络/任务状态依然不得改变几何。
- 导航取消、未知高度 prepend 与长块重排是组件必须通过的门槛，不在文档中预先宣判成功。
- 需要后端权威控制快照而现有 API 无法提供时，作为明确依赖提出，不假装前端能够凭缺失事件证明当前队列。
- 本方案没有购买/更换商业组件，也没有修改运行代码。完成方案不等于完成重构。

## 15. R2：把审核阻断转成可执行合同

本节不是给现有Hook再加判断，而是定义替换后的完整入口。与前文R1待决措辞有冲突时，以本节明确决定为准。

### 15.1 阅读会话：一个权威，过程不拥有定位权

ReadingSession的持久部分为`{key, revision, mode, bookmark, choices}`；
key包含principal/channel/view，mode仅following/browsing。运行部分另含activationID、inputEpoch和navigation。
loading、hydrating、restoring不属于阅读mode。navigation是`idle/resolving/issued/completed/cancelled/failed`，
不能用“调用了API”作为completed。

| 输入 | 阅读mode/目标 | 过程与后续动作 |
|---|---|---|
| activate | 显式目标优先，其次保存意图，无记录才following | 初始目标每次activation决策一次；后续数据不重新决策 |
| history/live/cache/meta成功或失败 | 不改变 | 更新数据/同步义务；没有导航输出口 |
| 主列表向上/浏览/操作消息内容 | browsing，inputEpoch递增 | 取消resolving和已issued的旧导航；保留当刻位置 |
| 主列表向下 | 仍browsing或维持following | 仅登记本次用户运动证据，不持久arm未来任意atBottom |
| 本次用户运动确实到尾 | following | 必须同时匹配inputEpoch、geometryRevision和原生运动来源 |
| 回最新 | following，明确latest目标 | 新导航替换旧导航；同步校准独立发起，不等待后端才响应按钮 |
| 恢复页失败/取消/暂缺 | 保持现有mode和可用位置 | navigation.failed/cancelled或继续resolving；不调用latest |
| 已证明目标删除/失权 | browsing或关闭失权页面 | 存活后继→前驱→已知空；不得将暂未加载当已删除 |
| filter/view变化 | 新view自己的会话意图 | 无保存意图时尝试保留当前可见语义项，再取邻项；只有明确“去最新”才跳尾 |
| suspend/deactivate | 保存有效revision | 所有旧activation命令失效；数据可继续归入其频道，不控制新页面 |

用户运动证据由组件输入边界持有，包含`gestureID/inputEpoch/geometryRevision/direction`。
wheel/键盘只在浏览器将对主列表执行默认滚动时登记；内部可滚内容、编辑器和已preventDefault事件不登记。
触摸惯性延续同一手势；pointer滚动条使用实际原生位移。结构/容器变化使旧geometryRevision证据失效。
无法证明某次atBottom来自用户运动时保持browsing；不得为“方便回尾”把迟到几何猜成用户意图。

### 15.2 不可变展示与单一提交协调入口

1. Replica先接受幂等事实并产生change-set，原始事实不因投影候选过期被丢弃。
2. Presentation维护实体依赖索引：request/response/child/分组事实→受影响消息实体→受影响内容块。
   正文、状态和拓扑分别有revision；呈现输入不能带读可变turn的getter。未变实体与已完成内容块共享引用。
3. 有序索引仅因结构变化更新；逐token只失效对应消息未完成块。Markdown回改前文按真实影响扩大失效范围，
   不能假定全部stream都是append。首次历史构建允许有界分批工作，不能让输入事件同步完成全频道扫描。
4. 发布的`PresentationSnapshot{epoch,viewID,revision,orderedIDs,entities,changes}`与旧版本隔离；
   choices另有revision并参与渲染输入。旧快照的字段在发布后不可改变。
5. 提交协调入口只配对已准备的展示版本和**提交时当前**ReadingSession。
   baseRevision失效就从最新Replica重算受影响项；readingRevision变化只重新授权preserve/follow，不丢消息。
6. React render纯读取同一版本快照，副作用在提交期进行；外部store采用稳定快照订阅。
   不在render过程中写“当前渲染函数ref”供已经提交的行跨版本读取；MessageItem按自己的实体/choices版本订阅。
7. 组件接收原子的`commit{activationID,baseRevision,nextSnapshot,inputEpoch,readingRevision,policy}`。
   issued导航另走命令口；数据commit里不能凭空生成导航。每次commit有accepted/rejected结果，重复id幂等。

会话保存用条件写`save(key,activationID,expectedRevision,next)`；卸载不拥有最后写胜出的特权。
跨tab草稿用独立draftRevision与冲突分支，不能静默覆盖正在编辑的文本。读前沿、同步覆盖、阅读书签是三个不同字段。
过滤视图不自动推进无法证明连续可见的频道级已读cursor；显式“标记已读”另有用户授权。

### 15.3 内容结构与输入保护

虚拟item仍是消息实体，稳定内容块用于内部锚点和局部渲染，不把每个token或段落无条件提升为列表项。
块ID由解析树的存活节点匹配产生：相同输入版本复用；未改写前缀/后缀按内容与邻接匹配，歧义时新建ID而不谎报存活。
阅读书签依次使用可见文本位置`messageID/blockID/textOffset`、块边界、消息边界、邻项。
内容自身被改写/删除时语义降级；不能冻结后台正文或要求用户点“接受更新”来掩盖困难。

媒体、代码和图表明确自己的尺寸容器；异步结果校验source/contentRevision，旧宽度测量不得跨layoutRevision复用。
不能把固定图框当作任意字体/Markdown变化都稳定的证明。用户明确resize或折叠时执行同一组件事务，
保住仍存在的语义内容，不强求被删除内容的像素位置。

选择/编辑保护属于组件物化合同：活动编辑item及当前原生选择涉及的已加载item不能被普通回收移除。
释放条件是编辑结束/焦点明确移出、选择折叠或用户清除；失权/删除优先撤销内容并明确告知，不能保留越权DOM。
普通选择在已加载阅读窗口内保留；“选择任意多页尚未加载历史”不是浏览器原生选择的承诺。
需要超出有限交互窗口的全文操作走显式文档/复制能力，不用无限pin扩大主消息列表。
必须在组件验收中确定交互窗口预算，并保证超限不会静默清除已选择的内容；不能用此预算降低普通长文复制可用性。

### 15.4 MessageList事务扩展：机制、位置与删除范围

**这是设计为新增的组件能力，不是现有Virtuoso API说明。**
保留成熟引擎的尺寸索引、ResizeObserver处理、虚拟范围和渲染设施；
增加一个事务调度入口，合并原有prepend、resize、following与index navigation的坐标写入权。
尺寸与偏移仍只在引擎内部存在，业务store不保存第二份尺寸树，也不预测量隐藏DOM。

接口固定为：

```ts
commit(update: ListCommit): CommitResult;
navigate(command: Navigation): void;
takeUserControl(inputEpoch: number): void;
onNavigationResult({id, status: 'completed'|'cancelled'|'failed', reason?}): void;
onReadingObservation({anchor, atTail, origin, inputEpoch, geometryRevision}): void;
```

内部事务步骤：

1. **捕获**：在旧DOM仍在、即将提交的边界读取当前真实scroll位置和可见内容锚点；
   不读取网络请求开始时的坐标。锚点优先文本/块，退化为消息；记录native位置用于扣除用户运动。
2. **身份映射**：根据稳定itemID和layout输入版本重映射引擎自身尺寸记录；删除项释放，未变项复用，
   新项与变宽项标为未知。中间insert/remove/混合变化进入此步骤，不谎报成firstItemIndex纯前缀。
3. **保留可见物化区**：本事务提交与测量前，保留当前锚点和必要旧可见节点；
   将其与引擎新范围合并为临时保留范围。这个范围由同一引擎渲染，不另造隐藏树，不重挂存活key。
4. **应用与测量**：React提交新内容，使用引擎的实际DOM测量刷新尺寸。未知屏外行可以估算，
   但估算不是移动阅读目标的授权，也不能让估计索引把当前已显示窗口换成空白。
5. **一次裁决**：重新核验inputEpoch/readingRevision；只有当前following可尾随，只有有效导航可定目标，
   其余保持本次当前锚点。以新旧锚点实际屏幕差校准组件坐标，扣除捕获后发生的原生运动，
   结果钳制到合法范围。校准由引擎内部唯一执行器在绘制前完成，不能再同时跑旧deviation补偿。
6. **完成**：发布geometryRevision与结果，释放临时保留范围。后续媒体/未知行测得高度是新几何事务，
   使用新的当刻锚点，不重放旧事务坐标。没有变化不重复提交，没有有效尺寸不使用零值重置。

运动与保位的方程：捕获时锚点屏幕坐标为Y0，捕获后原生用户运动为u（向下scroll为正），
则目标屏幕坐标为`Y*=Y0-u`，不是Y0。布局后的实测坐标为Y1，唯一执行器的修正为`Δscroll=Y1-Y*`。
原生运动通过同一容器实际位置及组件已记录的内部写入区分，不从wheel.delta猜测像素；
无法得到同一布局版本的一致观测时取消旧计算、捕获当前窗口，不重放旧offset。
删除/缩短导致Y*物理不可达时采用合法范围钳制并保持browsing。这排除“异步保位把用户刚滑的距离抵消”的模型错误。

用户接管不是“发一个反向定位”：`takeUserControl`同步递增组件接受的inputEpoch，
取消该epoch以前的index重试订阅、定时器及待执行rAF，清空导航目标并回报cancelled。
每个延迟回调执行前还检查epoch，防止已经出队的回调绕过取消。组件自行产生的scroll事件标记为内部来源，
不能又被解释成用户到尾。取消不调用scrollToIndex去当前位置，避免创建一个新的迟到目标。

对照当前上游实现的改动位置：

- index navigation系统已有内部清理函数；向组件事务口暴露取消并贯穿commandID/inputEpoch，结果从实际完成处回报。
- `beforeUnshiftWith`/`shiftWithOffset`和上滑resize补偿在事务模式下由上述同一入口替代，不能在外层叠加校准。
- `followOutput`及`scrollIntoViewOnChange`的延迟动作在事务模式下不再独立发命令；following由commit授权执行。
- 尺寸记录重映射与临时保留范围属于引擎size/list-state内部，业务应用不读写其索引树。

扩展不重写尺寸数据结构、滚动输入模拟、窗口回收算法或浏览器惯性；不提供业务网络/任务/缓存入口。
它仍是有维护成本的引擎集成，必须单独有上游基线、补丁清单和合同回归，不能把它包装成零成本适配。
G1由可取消命令生命周期关闭设计缺口；G3由稳定身份重映射和统一几何事务关闭；
G4由块内锚点与同一事务关闭；G2由引擎保留范围与内容交互生命周期承担。
这些结论是机制层设计，不代替真实浏览器对执行时序、惯性与资源预算的实现验证。

#### 技术复审裁决：采用受控扩展，拒绝伪装成原版能力

此处的架构决定由方案承担，不要求用户选择内部实现细节。选择依据是明确缺口，不是因为上游代码有rAF就认为它错误。

| 方案 | 能力/代价 | 裁决 |
|---|---|---|
| 原包公开API+薄业务层 | 现有索引定位有内部重试；任意结构变化与块内锚点未形成事务API | 不足以独自承诺全部合同，不作为完整方案 |
| 原包外再加业务scrollTop补偿 | 成本看似低，但补偿/跟随/导航多方竞争 | 禁止 |
| 继续自写MeasuredTimeline | 自己承担测量树、回收、惯性、物化、所有浏览器差异 | 停止此方向 |
| 成熟引擎内部事务扩展 | 复用底层引擎，但明确承担上游合并和扩展回归成本 | R2选定路线，扩展有独立维护边界 |
| 未核实的另一个组件/商业产品 | 不能以产品名称推定取消/混合更新/块内能力；授权也未确定 | 不作为未经证据的捷径，不购买 |

扩展只启用于会话的**单列、纵向、非Grouped/非Table、独立scroll容器**模式；
没有必要把所有上游组件组合一并重做。事务模式外维持上游行为，但同一个实例不能在两种模式之间热切换。

| 上游系统落点（当前安装实现可核对） | 必需变更 | 保留/禁止 |
|---|---|---|
| index navigation系统的内部清理和完成信号 | commandID/epoch、同步取消入口、回报；所有延后回调检查令牌 | 保留索引定位计算；禁止业务以“再定位当前位置”模拟cancel |
| size系统的sizeRanges/sizeTree/offsetTree | 稳定itemID→新索引的尺寸重映射，layout输入变化标未知 | 保留上游尺寸树；没有外部持久行高库或应用前缀和 |
| listState与items渲染 | 临时保留锚点窗口/显式导航目标窗口及活动选择范围 | 常态范围仍由引擎计算；不得把两个窗口间所有行强制挂载 |
| measurement/commit入口 | 捕获→提交→实测→单一裁决→完成；拒绝零尺寸与过期layoutRevision | 引擎唯一接收真实尺寸；不加隐藏副本预测量 |
| beforeUnshift/shift/resize/follow调度 | 事务模式禁用原独立坐标动作，改由同一事务执行器 | 禁止新执行器与旧补偿并跑 |

临时不连续窗口由引擎自身输出有序渲染段与中间占位；尺寸观察明确只读带item身份的行，
不能把占位当消息测量。最多保留“当前可见窗口+目标窗口”两段事务窗口，完成/取消立即释放。
选择保护范围属于交互保留而非常态overscan；不能因为活动选择阻塞已经可见消息的更新。
长距离显式导航未准备好时保持原窗口，目标窗口准备好后一次执行；用户接管则取消并释放目标窗口，原窗口不丢。

资源证明按支持负载而非无限输入：常态DOM由视口和物化预算限定；事务窗口最多两段；
活动编辑仅保留所在item；原生选择的保留量随已选已加载内容增长，**不能同时承诺任意长度原生选择和固定DOM上界**。
该例外单独计量，不把它叫作正常回收泄漏。超大跨历史全文操作采用显式复制/导出，不为后台同步增加无限保留。
不在用户仍有选择时静默清掉选择以通过性能测试；具体支持负载与超限提示在组件验收前固定。

设计复审通过的是上述单一职责和可实现的机制分解；不是证明实现只有几行，也不是原版组件合格声明。
若实施时发现需要重写底层尺寸树/惯性/常态虚拟范围算法，已超过本设计批准范围，必须回到技术选型，不能继续扩大自写引擎。

### 15.5 同步不是一次调用，而是有终态的义务

每个有用户兴趣的频道持有：`interestRevision/probedRevision/headTarget/coverage/workState/retryState`。
状态转移为`needs-probe→probing→needs-catchup→catching-up→current(H)`；
任一步可进入offline/retryable-error/forbidden。current只表示已完成有限目标H，不表示以后无需校准。

- 进入、重选、回前台、显式追最新更新interestRevision；即使相同请求在途，也不能吞掉新版本。
- Meta响应只结束它捕获的兴趣版本。响应后发现新兴趣则再校准一次，不为每次动作并发开一个请求。
- 查询失败保留义务。在线瞬时失败有限退避，离线等待可用事件；永久权限错误终止并展示，不无限计时重试。
- 当前活动频道有有界的新鲜度复核；后台频道只保留低成本兴趣/恢复事件，不让计时器挤占用户交互。
- Meta给出有限head H；依据扫描覆盖找缺口，不把“有最大seq”或“可见seq不连续”当证明。
  到H即发布完成；新H合并为下一轮义务。上翻历史有独立cursor与最低推进预算，不能被持续live永远饿死。
- 远端页面先入Replica，再发布一致投影。持久行与coverage同事务；内存前沿、持久前沿、已读前沿独立。

attach拆成关键同步安装与非关键持久化：关键身份/Meta安装失败不得宣布attached；缓存失败不关闭合法live。
服务端先安装订阅，再为每个频道独立捕获head/seam并启动该频道的live；目录元数据增量公布。
每频道明确初始seam就绪或失败，慢频道不挡其他频道；不能仅提前LaunchFeed而丢掉订阅与快照之间的事实。
新协议与旧协议采用显式版本能力协商，旧服务只报告旧模式，不假装提供增量seam。

### 15.6 后端控制投影与发送意图分离

控制同步输入选择**权限过滤的当前任务快照+版本化增量**，不是让客户端扫描无限历史寻找terminal。
快照包含`dataEpoch/channelID/controlRevision/activeTasks/complete`；增量包含`baseRevision/nextRevision/upsert/remove`。
订阅先于快照边界建立；增量可暂存于有界队列，连续接续后成为current，发现缺口重新取快照。
如果现有后端能力可复用，映射到同一合同，不另立竞争权威；快照构建来自后端生命周期投影，
不能为了响应一次请求重扫整个账本。任何task ID的版本回退均拒绝，删除表示该快照语义下不再活跃。

ControlProjection的unknown/stale/current三态独立于消息historyReady。未知不是空队列；
旧消息缓存只用于阅读，绝不灌回activeTasks。等待区展开偏好仍由Choices保存；
断线/校准文案进入固定状态占位，不改变默认展开、输入框位置或消息尺寸。
控制命令带task身份和期望版本，后端重新校验权限与合法状态；前端点击后仅标pending-command，不乐观伪造终态。

Submission则保存用户本地意图：`draft→durable-queued→transmitting→accepted→landed`，另有uncertain/rejected。
IndexedDB事务成功才清空对应draftRevision；失败保留原稿和附件。保存期间用户继续输入时只清除已接受版本，
不清掉后来输入。clientMessageID贯穿重试/receipt/feed，feed可先于receipt到达，landed不得回退accepted。
local echo与正式消息按同一呈现身份合并，不因拿到seq再次插入一行。本地待发送不冒充后端queued。

### 15.7 已确认布局：内容驱动尺寸，状态不驱动尺寸

2026-09-16，用户明确同意：输入、回复、附件自然增高时可以调整消息区可用高度，同时保持阅读位置；
断线、排队等状态绝不调整。原先“无论输入怎样增长，消息底边都固定”的分支撤回，不再作为实施选项。

固定状态栏、等待区贴输入框、自然回复/输入高度、移动目录独立、32px间距、原默认展开与外观均保留。
尺寸来源只有两类：用户内容/展示选择，以及实际可视窗口环境；后台状态无尺寸写权限。

| 变化来源 | 允许的尺寸行为 | 阅读行为 |
|---|---|---|
| 输入换行、回复/附件增删、用户主动展开/收起 | 更新输入栈期望高度，经Surface分配实际高度 | browsing保持存活锚点，following保持尾端，不新增导航 |
| 连接/断线/排队/处理中/错误文案、后台任务条目数量变化 | 在既定状态/等待内容槽内换内容或内部滚动；不增减外部占位 | 不改变视窗边界或阅读意图 |
| 键盘、横竖屏、窗口/分栏宽度改变 | 根据有效可视视口重新计算预算，拒绝隐藏时零尺寸 | 保语义位置；范围不足时合法钳制，不伪造following |

等待区外部尺寸由用户展开偏好和Surface预算决定，不由queued条目数量决定。
相同展开偏好下，空、未知、一条、多条任务共享同一预留槽，内容超出内部滚动；
不通过后台出现/消失整个槽来推动输入框。槽的尺寸与原外观由布局token定义，不锁死用户主动展开操作。

尺寸合同：H为扣除Header/安全区后的实际可用高度；M为设计token指定的最小阅读高度；
O为分配给整个输入栈的实际高度（含回复/附件/等待区/固定状态栏）；G=32px。
正常支持范围内满足`O ≤ H-M-G`，阅读视窗高度为`V=H-O-G`，底边在实际栈上沿32px处。
输入框与等待区保持一个栈，不分别向消息列表写margin、padding或scrollTop。
Surface是唯一容器尺寸owner；MessageList只接收真实容器变化并保位，没有尺寸反馈回Surface的闭环。

分配规则：先保证编辑器、发送/取消控件、状态栏及展开等待区的必要操作高度，
再将剩余预算分配给输入/附件/等待内容；达到预算后内容内部滚动，不继续覆盖阅读区域。
当软键盘等使H连必要操作高度+M+G都容不下时，不声称两块内容可同时完整显示：
外层Surface提供有限内容滚动以让必要控件和阅读区分别可达；它不是消息列表定位器，也不清空消息。
恢复可用空间后恢复正常分配，同一阅读会话和输入法状态保留。极限尺寸是明确环境降级，不是网络状态例外。

同一次内容尺寸/消息更新先合成最终容器尺寸与展示版本，再交给第15.4节事务；
没有180ms高度动画，没有同步/microtask/rAF三套钉底，不以resize引发的atBottom为用户到尾证据。
证明边界：在`H ≥ 必要操作高度+M+G`时上述分配直接满足V≥M和不遮挡；
极限尺寸按明确的外层可达性降级，而不是用负高度或覆盖消息假装约束成立。

结论：R2的状态权威、事件/并发合同、同步与控制协议、组件事务机制及已确认布局完成静态复审，
