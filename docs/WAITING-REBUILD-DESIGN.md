# 等待区重建方案

## 1. 等待区回答的唯一问题

**「我交给 Agent 的这件事，现在还欠着吗？」**

它不是一个列表控件，是一个判断的呈现。判断错了，界面怎么做都没用。

## 2. 账本上有什么（本频道实测，2026-09-22）

一条发给 Agent 的请求，账本上能出现的行只有三类：

| 行 | 内容 | 实测 |
|---|---|---|
| 请求 | `agent.ask` / `agent.queue`，带 `expires_at` | seq 132760 `ts=1790082057364` `expires_at=1790168457364`（+24 小时） |
| 过程帧 | `{status: queued\|processing, controls:[...]}` | seq 132761，**请求之后 1 毫秒**，带 `[replace, dismiss, steer]` |
| 终态 | `{status}` 或 `{merged_into}` / `{replaced_by}` / `{preempted_by}` | seq 131125 `{status:failed, error_code:unanswered_timeout, cancelled:true}` |

心跳会再发 `queued` 帧（`heartbeat:true, position:N`），那是刷新，不是第一帧。
**第一帧 1 毫秒就到——盲窗不存在，之前认为要等十几分钟是我读错了心跳帧。**

## 3. 准入规则

```
在等待区  ⟺  ① 账本上有明确的位置事实（queued / received / deferred）
                或 本机出站队列里还没发走
          ∧  ② 没有终态
          ∧  ③ now < expires_at
```

三条腿全部只读**持久**来源：账本（内存副本 + IndexedDB 缓存）和出站队列（IndexedDB）。
**没有任何一条依赖会话内存。**

## 4. 僵尸的四种来源

| 来源 | 挡它的腿 |
|---|---|
| 往上翻历史翻出的旧请求，终态在没加载的区段里 | ① —— 旧行没有位置事实就进不来 |
| Agent 死了，终态永不到来 | ③ —— 24 小时后自动离场 |
| 十万 seq 之前排过队、再无后续 | ③ —— 同上 |
| steer / interrupt 之后别的终态没来 | ③ —— 它们各自是独立请求，各有自己的 24 小时 |

**旧版只有 ① 和 ②，没有 ③**（它算过 `expired`，但只拿去决定按钮亮不亮，不决定去留）。
所以旧版的第 2、3、4 类僵尸会永远住在等待区。这一条我们比旧版严。

## 5. 过期的行去哪

**必须两边同时改，否则消息会两边都不在。**

- 等待区：过期 → 踢出
- 时间线：过期 → **不再让位给等待区，作为一条未答的消息重新显示**

判断写在 `conversation-visibility.js` 的 `requestExpired()`，等待区和时间线读同一个。
今天三次事故都是同一个形状：一个事实两份副本，只改了一份。

## 6. 恢复能力

刷新、热更新、组件重挂、标签页崩溃重开——重算一遍，结果相同。
因为输入只有账本和 IndexedDB，两者都不随页面生死。

原来还有第三个来源：一个只活在 React state 里的集合。**它是今天等待区反复消失的唯一原因**，
每次热更新清零一次。已删除。

## 7. 现状

**已落地**

- 等待区来源改为「账本位置事实 + durable 出站队列」，无内存态
- `requestExpired` 第三条腿，等待区与时间线共用
- 排序键统一为请求自身 `ts`（原来是 `requestSeq || ts`，两种量纲混用，落账瞬间行从列表底窜到顶）
- 控制按钮：只看账本声明了哪些控制词，不再要求对方额外声明 payload、也不再要求名册已确认

**还缺**

- **过期的重算时机**：现在只在账本推送触发的重渲染里重算。24 小时的期限下够用，
  但一个整天挂着不动的页面里，过期的那条会多留一会儿。要精确就需要一个粗粒度定时器。
- **加载区间（coverage）没挂到 `state` 上**：`headSeq` 和已加载区段 replica 已经在算
  （`mergeReplicaCoverage` / `materializedCoverage`），但没暴露给等待区。
  只有将来想去掉 ①「必须有明确位置事实」这个条件时才需要它——现在不需要。

## 8. 明确不做的

- **不从"没有终态"直接推断"在等待"**。历史回填会把整页旧请求倒进来。
- **不靠会话内存兜任何一段**。它活不过一次热更新。
- **不在前端猜名册新鲜度**。账本上对方声明了控制词就给按钮、就发命令，拒不拒是对方的事。
