# GenSpark GenTeam 分层设计基准与 atoll-web 差距

状态：设计研究完成，尚未按本文施工
日期：2026-08-18
研究对象：已登录的 GenSpark GenTeam 工作区、三个官方 SAMPLE 频道及普通频道
上位规范：[PRODUCT-INTERACTION-MASTER-PLAN.md](PRODUCT-INTERACTION-MASTER-PLAN.md)
现有 UI 规范：[UI-INTERACTION-ARCHITECTURE.md](UI-INTERACTION-ARCHITECTURE.md)

## 1. 核心结论

GenSpark 的成熟感不主要来自配色、圆角或三栏布局，而来自一个贯穿全产品的对象模型：

```text
频道 = 一个持续工作的共享上下文
消息 = 工作发生和形成共识的主时间线
Thread = 围绕某条消息展开的局部工作区
文件 = 工作过程产生、修订和消费的产物
任务 = 从消息和产物中提炼出的可追踪承诺
管理 = 当前频道的上下文配置，而不是另一套后台
```

这些表面展示的是同一组对象，不是几个互不相干的功能模块。用户可以从消息看到文件的来源，从文件回到协作语境，从消息创建任务，在不离开频道的情况下查看成员和权限。

atoll-web 当前的根本差距是：后端事实虽然统一走账本，但 UI 又把账本、文件、KV、定时动作和管理拆回了若干工具面板。用户能完成操作，却看不到一项工作如何从请求变成过程、产物、任务和最终结果。

## 2. 第一层：整体产品设计

### 2.1 产品心智模型

GenSpark 首先是“人与 Agent 共同工作的频道”，其次才是聊天、文件或任务工具。用户进入频道后，所有高频工作都围绕当前频道展开：

- Chat 回答“发生了什么、谁在做、做到了哪里”；
- Files 回答“这个频道已经形成了哪些产物”；
- Tasks 回答“还有哪些承诺需要完成”；
- Channel details 回答“谁参与、如何通知、谁能改变成员关系”。

页面切换不会改变当前频道，也不会让用户重新建立上下文。

### 2.2 稳定空间与临时空间

稳定空间长期存在：

- 全局功能 Rail；
- 频道 Rail；
- 当前频道 Header；
- Chat / Files / Tasks 主视图导航。

临时空间按任务出现：

- Thread 右侧上下文；
- Channel details 右侧上下文；
- Create task 模态事务；
- 消息悬浮操作；
- 文件预览。

成熟点在于“不同生命周期使用不同容器”，不是所有功能都塞入右栏，也不是所有操作都弹窗。

### 2.3 Atoll 应采用的整体模型

Atoll 的独特价值是可审计账本、Agent 编排和结构化终态，因此不应复制成普通 Slack。目标模型应是：

```text
频道工作台
├─ 动态：可读的协作时间线
├─ 产物：账本中出现过的文件与结构化对象
├─ 任务：仍需行动的回合、审批、定时动作和失败恢复
└─ 上下文：成员、Actor、线程、对象详情和频道设置
```

协议细节仍可达，但不能成为一级信息架构。

## 3. 第二层：核心用户故事

### 3.1 多 Agent 完成一项工作

GenSpark 的 Broadway 示例不是展示四个 Agent 各自输出，而是展示一条完整协作链：研究员发现候选并附研究文件，用户做优先级决定，文案 Agent 补充偏好背景，助理把结果登记为持续清单，工程 Agent 建立手机提醒。

关键设计：

- 主时间线只保留团队需要共同知道的节点；
- 研究细节进入 Thread，避免污染主线；
- 文件紧跟产生它的消息；
- 结构化清单是可以继续操作的活对象；
- Agent 的主动动作有 `PROACTIVE` 标识，但仍服从统一阅读轴。

### 3.2 多文件协同修订

Budget Approval 示例展示了更重要的文件故事：模型、备忘录和演示稿先产生 v1；评审时间和预算条件改变后，用户在消息中做决策；不同 Agent 分别产生 v2；最后由另一个 Agent 做跨文件一致性审计。

这说明 Files 不是上传下载仓库，而是以下关系的聚合投影：

```text
需求消息
  → Agent 产出文件 v1
  → 条件变化
  → 人类决策
  → 文件 v2
  → 跨文件校验
  → 可交付结果
```

### 3.3 从消息产生任务

Tasks 空态明确提示“Create a task from a message to get started”。任务不是与对话平行录入的孤立表单，而是从已有语境中提炼出来。独立新建任务仍然存在，但表单只要求自然语言描述，并把负责人作为次级选择。

### 3.4 查看和管理频道

Channel details 在右侧打开，内容按阅读频率排列：成员与添加入口最先出现，通知和成员权限其次，邀请链接与频道信息最后出现。危险、低频、基础设施字段没有占据主视图。

## 4. 第三层：信息架构

| 层级 | GenSpark 对象 | 用户问题 | Atoll 目标 |
|---|---|---|---|
| 全局 | Chat、Activity、Members、Computers、Connectors | 我要去哪类工作？ | 协作、活动、主体、设备、连接器 |
| 频道 | Channels、Direct messages | 我正在哪个共享上下文？ | 我的频道、空间、私有/直接协作（后端支持后再开放） |
| 主视图 | Chat、Files、Tasks | 我要看动态、产物还是承诺？ | 动态、产物、任务 |
| 局部上下文 | Thread、Channel details | 这条消息/这个频道的详情是什么？ | 线程/回合详情、对象详情、成员与设置 |
| 短事务 | Create task、Create channel | 我要创建一个对象 | 模态输入，提交后回到对象上下文 |

当前 atoll-web 把“文件”和“任务”显示为主视图 Tab，却实际打开右侧工具面板。这违反了标签所表达的空间预期：用户点击主视图导航，应该看到占满主工作区的文件或任务内容，而不是仍然保留账本、再叠加一个配置抽屉。

## 5. 第四层：主交互区设计

### 5.1 消息区

GenSpark 特点：

- 所有成员沿同一左边缘阅读，不做左右气泡；
- 身份、AI 标识、时间与主动状态构成一行轻量元信息；
- 正文无外框，只有文件、结构化对象、警告等获得实体边界；
- 消息操作默认隐藏，悬浮后出现 reaction、reply、thread、edit、more；
- 系统事件压成单行，不伪装成成员消息；
- Thread 在右侧并列，复制根消息并提供“View in channel”返回来源；
- 输入器是一个完整编辑表面，附件、表情、格式和发送选项都属于输入器自身。

Atoll 当前差距：

- 已完成平面化，但仍以“请求 + 技术过程 + 终态”作为主要组织单位，缺少面向用户的工作叙事层；
- 没有 Thread/回合详情和来源返回；
- 没有消息悬浮操作，也不能从消息提取任务；
- 附件能显示，但文件与生成它的回合、版本和后续使用缺少关系；
- Composer 仍像单行命令入口，附件和富编辑能力较弱。

### 5.2 文件与产物区

GenSpark 特点：

- 文件首先以内联附件出现在来源消息下；
- Files Tab 是当前频道所有文件的聚合视图，不是上传表单；
- 文件行优先展示文件名、作者、时间、类型、大小；
- 点击整行进入预览，更多操作收进局部菜单；
- 文件版本通过时间线叙事自然表达，用户知道为何产生 v2；
- 表格/清单等结构化产物不必伪装成普通文件，可以成为可交互对象。

Atoll 当前实现的主要问题：

- `FilesPanel` 首屏是 ticket、daemon、路径和 PUT 阶段，暴露了实现机制而不是用户目标；
- 文件只保存在组件的 `useState` 中，标题也明确是“本次会话文件”，刷新后无法成为频道资产；
- Files Tab 实际打开窄 Context Pane，文件列表没有获得主工作区；
- KV 与文件被并列包装为“资源”，这是后端分类，不是用户分类；
- 上传、下载、附加到消息是三个按钮动作，缺少拖拽/选择文件后直接进入消息草稿的主路径；
- 没有预览、来源消息、作者、时间、版本、使用位置和状态过滤。

目标设计：

```text
产物主视图
├─ 顶部：搜索 / 类型 / 作者 / 时间 / 上传
├─ 最近产物：文件、结构化结果、清单
├─ 文件行：预览 + 名称 + 来源 + 作者 + 时间 + 类型/大小 + 更多
└─ 详情上下文：预览、来源回合、版本、下载、附加/引用
```

普通用户路径应是“选择文件 → 出现在消息草稿 → 随消息入账”；daemon 和 ticket 只在失败诊断详情中出现。KV 应进入“数据对象”或开发者工具，而不是占据 Files 的默认首页。

### 5.3 任务区

GenSpark 特点：

- Tasks 是占满主区的对象列表；
- 默认区分 For you / All，并提供状态过滤；
- 空态直接教用户从消息创建任务；
- 独立创建只先收自然语言，负责人是次级字段；
- 任务和消息存在来源关系。

Atoll 当前“任务”实际是本地定时消息配置器：需要毫秒、消息类型和 JSON payload。它是调试工具，不是用户任务产品。

Atoll 应先拆分概念：

- 工作任务：来自消息回合，包含负责人、状态、来源、截止/等待条件；
- 待审批：需要人类决定的账本对象；
- 自动动作：定时或条件触发的技术能力；
- 运行中 Agent 回合：可取消、调整方向或等待终态。

四者可以汇总到“任务”视图，但必须用类型和状态区分，不能都叫定时动作。

### 5.4 管理区

GenSpark 特点：

- 频道详情是右侧上下文，不替换 Chat / Files / Tasks；
- 先展示成员，再展示通知和权限，最后是邀请与基本信息；
- 开关附带后果说明，不展示底层字段名；
- 添加成员是就地入口，不先让用户选择 human/agent/tool 技术类别。

Atoll 需要保留 human、agent、tool 的真实差异，但应在“添加参与者”的候选列表中用能力与身份标识表达，不应让类型选择成为第一步。退役、重启、移除等动作继续保留明确确认和账本结果。

### 5.5 导航与输入区

- 全局 Rail 只放跨频道目的地；频道 Rail 只放频道与直接协作；
- 频道 Header 只表达身份、搜索、成员和低频操作；
- 主视图 Tab 永远替换中间内容，不能偷偷打开右栏；
- 输入器固定属于 Chat，Files 和 Tasks 不应继续显示消息输入器；
- 所有对象详情使用同一 Context Pane，并保留返回来源。

## 6. 第五层：视觉线条与布局规则

在 1280×720 的实测页面中：

- 全局 Rail 约 53px，暖灰 `rgb(245,241,234)`；
- 频道 Rail 约 321px，更浅暖白 `rgb(251,248,241)`；
- 主区占余下 906px，纯白；
- 两条 Rail 之间主要依靠极浅边线分层，不使用大阴影或悬浮卡片；
- 主导航 Tab 高约 38px，激活态依靠文字和底线；
- 普通消息字号约 15px，透明背景、透明边框；
- 卡片半径存在但边界只在 Hover 或实体对象上发挥作用。

视觉语法：

1. 大区靠背景色和单像素分隔线建立层级；
2. 普通内容靠留白分组，卡片只授予“可操作对象”；
3. 黑色负责信息，暖灰负责环境，强调色负责状态和关键动作；
4. Header、Tab、内容和 Composer 各有稳定水平线；
5. 文本最大阅读宽度受控，编辑器可以比正文更宽；
6. 操作在 Hover/Focus 时出现，静态页面保持低噪音。

响应式不是等比缩窄：

- 800px：53px 全局 Rail、321px 频道 Rail 仍保留，主区缩为约 426px；
- 600px：两级 Rail 隐藏，主区占满 600px；
- Thread/Details 在中等宽度接管主工作区，在更窄宽度接管全屏。

Atoll 不必照抄 321px，但必须采用“表面替换状态机”，而不是让每一栏都缩到勉强可见。

## 7. 差距优先级

| 优先级 | 改造 | 原因 |
|---|---|---|
| P0 | 让动态 / 产物 / 任务成为真正的主视图 | 当前 Tab 与实际空间行为不一致 |
| P0 | 建立频道挂载目录视图，并在其上叠加消息引用索引 | Atoll 已有每频道文件根，不能用竞品的产物库模型覆盖真实目录 |
| P0 | 建立消息—附件—结构化终态—任务的来源关系 | 这是跨区连续体验的基础 |
| P1 | Thread/回合详情 Context Pane | 把技术过程和局部讨论从主线移走 |
| P1 | 文件预览、元信息、来源、版本和更多操作 | 让文件成为工作对象而非 ticket |
| P1 | 任务统一视图与“从消息创建”入口 | 把承诺从聊天中提炼出来 |
| P1 | Composer 升级为完整编辑表面 | 附件和消息必须是一条主路径 |
| P2 | 全局搜索、频道内搜索、Activity | 对象增多后才有必要 |
| P2 | Hover 操作、reaction、saved | 提升效率，不是对象模型前提 |

## 8. 完整场景验收

用下面的 Atoll 场景验收新体系，而不是只验收组件截图：

1. 用户在项目频道 @Researcher 请求竞品研究；
2. Agent 显示工作中，过程详情可在右侧查看，主时间线保持简洁；
3. Agent 返回报告文件和结构化对比表，两者紧跟终态出现；
4. Files 视图在当前频道挂载目录中显示真实文件，并对被消息引用的文件保留来源回合；
5. 用户预览报告、在来源消息开 Thread 要求修订；
6. Agent 产生 v2，产物详情显示版本关系而非两个无关文件；
7. 用户把“周五前验证三个结论”从消息创建为任务并指定 Actor；
8. Tasks 视图显示负责人、来源、状态和截止时间；
9. 权限被撤销时，动态、文件和任务均保留只读事实，所有写动作一致禁用；
10. 在 600px 下，主视图、Thread、文件预览和管理逐层全屏进入且可返回原来源。

如果上述任一对象需要用户重新输入频道、Actor、文件或请求 ID，说明跨区对象关系仍未建立。

## 9. 被推翻的假设

1. “先把消息改平、右栏改暖就接近 GenSpark”：错误。这只能改善观感，不能建立工作连续性。
2. “Files 是上传下载功能”仍然错误，但“Files 等于 GenSpark 式产物库”同样错误。Atoll 的第一事实是频道默认挂载目录；消息引用、预览和追溯是叠加语义。
3. “后端叫 resource，所以 KV 和文件应该同页”：错误。后端执行模型不能直接决定用户信息架构。
4. “Tasks 可以先用定时动作顶替”：错误。定时器是自动化能力，任务是可追踪承诺。
5. “所有账本过程都应在主时间线中折叠展示”：不完整。折叠只减少噪音，成熟方案还需要可定位的回合详情和 Thread。
6. “添加成员应先选 human/agent/tool”：错误。用户先选择参与者，类型是候选对象的属性；只有创建新 Actor 时才需要类型决策。

## 10. 施工边界

本文是设计基准，不表示上述能力已经实现。施工前必须先完成三项设计：

1. 频道文件模型：resource list prefix 提供挂载目录事实，feed/终态/附件只建立可重放的引用索引；
2. 工作任务模型：明确它与现有 timer、approval、running turn 的关系；
3. 对象来源模型：统一 `channel_id + request_id/turn_id + entry_id + resource_id` 的导航和恢复语义。

完成这三项后再改页面，否则只会再次得到一组外观相似、内部仍然碎片化的组件。
